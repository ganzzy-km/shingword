# PATCH-INTEGRATED-S4-OCR-RELEASE — S4 메인 분석 검증·고정밀 OCR 개선·STAGING 전체 점검·운영 적용

## 0. 단일 작업의 최종 목표와 실행 권한

사용자가 승인한 이 작업을 하나의 연속된 Codex 실행 단위로 끝낸다.

1. 현재 글빛 1.1.0 운영본과 최신 STAGING/개발 후보를 정확히 대조한다.
2. 기존 S4 분석 엔진의 기능·정확성 계약·실제 응답 성능을 검증한다. 관련 결함이 확인되면 수정하고 재검증한다. 기준을 통과한 S4를 글빛의 단일 메인 분석 엔진으로 사용한다. 이미 메인으로 실행 중이면 중복 설치·중복 엔진을 만들지 않고 활성 경로를 검증한다.
3. 기존 일반 OCR은 빠른 경로로 보존하면서 고정밀 OCR을 실제 문학자료의 원문 보존·구조 복원·인식 정확도 측면에서 가능한 한 개선한다. 추정에 의한 문자 자동 교정은 하지 않는다.
4. STAGING에 실제 구현된 **제품 기능 전체**를 단일 후보·실제 API·브라우저·DB를 통해 최종 검증하고 발견한 범위 내 결함을 고친다.
5. 필수 안전·기능·통합 Gate가 모두 통과한 **하나의 검증된 배포 후보만** 운영에 적용한다. 운영 서비스는 모든 사전 검증이 끝난 뒤에만 공식 절차로 중지하고, 변경을 적용한 다음 재시작하여 사용자 접근을 복구한다.
6. 운영에서 실제 실행 프로세스·파일 해시·주요 기능을 확인한다. 실패하면 현재 운영 데이터 보존을 전제로 복귀 또는 안전한 서비스 복구를 수행한다.

**이 지시에는 위 범위의 운영 소스·정적 빌드·고정 OCR 런타임 설정을 배포할 권한과, 검증 통과 후 운영 서비스를 계획적으로 중지·재시작할 권한이 포함된다.** 매 내부 단계마다 사용자에게 새 프롬프트나 재승인을 요청하지 않는다. 전체 개발 시간에 인위적인 제한을 두지 않는다. 단, 무한 재시도·무한 모델 실행을 하지 않으며 각 작업의 자원 한도·잠금·timeout은 유지한다.

이 권한은 운영 DB 삭제·재생성·과거 DB로 복원, 데이터 손실성 마이그레이션, 인증 우회·비밀값 변경, 계정 공개 범위 확대, 외장 디스크 포맷/파일 삭제, 새 유료 서비스, commit/push/merge, 미승인 기능 추가까지 포괄하지 않는다. 이러한 상황에서는 안전하게 수행 가능한 다른 검증을 마무리한 뒤 필요한 최소 사용자 결정을 하나로 보고한다. 운영 변경을 시도하기 전의 실패는 운영 서비스를 멈추지 않고 종료한다.

## 2. 배포 대상과 테스트 전용 기능을 구분하는 기능 인벤토리

**'STAGING의 모든 기능'은 현재 STAGING에서 실제 구현·등록·검증 가능한 글빛의 제품 기능을 뜻한다.** 문서에만 계획된 차기 1.2.0 원작품·논증 기능을 새로 개발하라는 뜻이 아니다. 기존 런타임에 포함되지 않은 기능을 완료로 표시하지 않는다.

STAGING 후보의 API route, 실제 메뉴, 저장 모델, 서비스 entrypoint, 빌드 소비자를 짧게 목록화하고 각각을 아래 상태로 구분한다.
- PRODUCT_RELEASABLE: 운영 배포할 제품 기능
- STAGING_ONLY: `/__staging__` 테스트 로그인·가짜 세션·fixture·QA 서버·시험 비밀값·시험 DB 경로·디버그 도구 등 운영 배포 금지
- DEVELOPMENT_ONLY: 과거 진단·실험 스크립트·테스트 산출물·개발 보고서 등 운영 배포 금지
- PLANNED_ONLY: 아직 코드에 없는 기능. 이번 배포 인벤토리에서 제외

인벤토리의 각 실제 제품 기능을 테스트 ID, 실제 실행/재사용 증거, PASS/FAIL/UNVERIFIED와 연결한다. 기존 route의 경미한 UI 문제도 재현하면 기록하고, 실제 필수 흐름 장애 여부에 따라 수정한다. 부주의하게 STAGING 설정·계정·업로드·백업·가짜 인증을 운영에 복사하지 않는다. 운영 1.1.0에 이미 적용된 기능과 STAGING 후보에서만 새로 구현된 기능을 비교하여 누락·중복 없는 최종 delta를 확정한다.

## 3. S4 분석 엔진 전면 검증과 필요한 개선

운영의 실제 분석 API가 어떤 구현·설정·프로세스에서 S4를 호출하는지 확인한다. 동일 분석을 처리하는 병렬/옛 엔진이 있으면 단순히 새 엔진을 추가하지 말고 승인된 단일 엔진 경로를 재사용한다. 현재 S4가 이미 활성이라면 그 사실과 해시를 검증하는 것으로 충분하다.

### 3.1 정확성·관계 계약
검증 대상:
- 분석 생성·저장·재조회, 글 버전·스냅샷·소유권 연결, 30,000자 장문, 글 수정 후 STALE/재분석
- CLAIM/EVIDENCE 후보와 E→C 관계, 근거 선행/후행, 복수 후보 경쟁·REVIEW, 기존 R0/R1 승인/보류 기준, R2는 DISABLED
- 이미 승인된 16관계 쌍 및 보존된 57개 회귀 조건의 변경 전후 일치; 기존 안전 기대값·Golden/자체 검증 corpus 보존
- 출처가 다른 작품의 근거 연결 차단, 장면 지시어 모호성 보존, 허위 승인 화살표 방지, 자동 질문·문자열·링크 대상·출처의 정확한 연결
- 사용자 작성 글·주석·인용 카드·공용 자료/비공개 자료와 분석 결과의 권한 일치
- S4 새 분석 ID가 실제 저장되는지. 종전 운영 후검증이 미완료였다면 STAGING 분석으로 이를 대체해 PASS 처리하지 않음

기존 S4에서 확인된 잘못된 자동 연결·질문·메모리 누수·명백한 비정상 지연 등의 최소 재현 사례가 있으면 원인 및 변경 영향을 밝히고 이번 격리 후보에서 최소 수정한다. 테스트의 단계 한정 기대값과 새 기능이 충돌하면 근거를 갖추고 명시적 계약 개정으로 구분하되 안전한 결과를 얻기 위해 점수·임계값·원문 보호·Golden을 무단 완화하지 않는다.

### 3.2 성능 합격 기준
동일한 30,000 코드포인트와 원작품 0/1/3개 조건으로 비교하고 새 최종 후보의 p50/p95, timeout, 프로세스/호스트 메모리와 동시 OCR 영향도를 기록한다. 조건별 독립 측정을 필요한 만큼 실시하되 개발 중 매 수정마다 장시간 전체 재측정하지 않는다.

참고할 과거 S4 p95 값(같은 프로토콜 검증 전 비교 기준으로 확정하지 않음): 작품0=1.153초, 1=21.159초, 3=30.890초. 이전 S3/S4 상대 1.5배 회귀 Gate가 현재도 적용 가능한지 원본 계약을 확인한다. 프로토콜·하드웨어·캐시가 다르면 같은 수치라고 비교하지 않는다.

S4_PERFORMANCE=PASS는 다음을 모두 만족해야 한다: 현재 승인 성능 계약 충족, 같은 입력의 기존 기준 대비 설명되지 않은 유의한 회귀 없음, 분석 실패/무한 대기/OOM 없음, 정식 분석 저장·조회·권한·질문 경로 정상, 허용 가능한 리소스 공존. 실제 문학적 정답률·일반 Precision/Recall을 별도 독립 라벨 없이 인증하지 않는다. 알려진 절대 응답 지연은 미해결이라면 남긴다. S4 계약이 통과하면 `PRIMARY_ANALYSIS_ENGINE=S4`를 확인/적용하되 내부 엔진 버전과 기존 분석 ID를 무리하게 교체하지 않는다.

## 4. 고정밀 OCR 기능·실제 품질·자원 개선

기존 Paddle 한국어, Tesseract best, PP-StructureV3, 선택 영역 PaddleOCR-VL, 일반 OCR 경량 경로, 텍스트 PDF 직접 추출, 검수 UI·불변 확정·S4 재사용을 재개발하지 않는다.

### 4.1 오류 분석 및 보완
- 실제 대상은 한국어 시·소설/산문·희곡·해설지 우선, 표·평가 기준표는 보조 범위
- OCR 결과의 **문자 오인식**과 **읽기 순서/시 행·연·들여쓰기/희곡 대사·지문/문단 직렬화 오류**를 분리한다.
- `compose_draft`와 `combine_page`·구조 정보를 동일 인식 출력에서 비교하여 구조 정보가 초안에 전달되지 않는 결함을 확인한다.
- Paddle/Tesseract 글줄 1:N/N:1·누락·겹침, 글줄/문단별 PSM6/7, 조건부 Paddle 재검출을 활용하여 실제로 오류가 의심되는 영역을 다시 확인한다.
- VL은 실제 OCR 메모리 예산이 확보된 영역만 선택적으로 실행한다. 기존 Job Object·자원 입장 검사·Worker 복구를 재사용한다. 사용자의 에세이 분석을 멈추게 하는 전역 메모리 경쟁을 만들지 않는다.
- 자동 초안 선택 정책은 정답 없는 상황에서도 관측 가능한 트리거와 원본 픽셀 근거가 있을 때만 제한적으로 사용하고, 실제 개발용 정답 자료에서 오수정보다 이득이 입증된 규칙만 반영한다. 불확실하면 자동 교정하지 않고 검수 후보로 남긴다.
- 이미지 근거 없이 `빛/빚`, 비표준 원문, 띄어쓰기·문장부호·인용부호·연 구분을 문맥으로 추측해 바꾸지 않는다. 원시 결과와 확정 판본은 보존한다.

### 4.2 품질 평가 계약
사용 허가가 확인된 실제 시·산문·희곡 자료의 검수 정답이 로컬에 있으면 작품·판본·스캔 그룹 단위로 개발/미사용 평가를 분리한다. 일반/고정밀 동일 페이지의 엄격 CER, 페이지별 최악값, 글줄·연/문단·대사 구조, 인용문 완전 일치, 누락·새 오수정, 검수 부담, 처리 시간과 최대 Job commit을 쌍체 평가한다. 평가 라벨을 보고 새 규칙을 튜닝하지 않는다. 외부 AI에 권리 없는 원문을 업로드하지 않는다.

현재 합성12페이지 자동 초안 양 모드 모두 `128/963=13.29%`는 합성 회귀 근거일 뿐 실제 문학 정확도 인증이 아니다. 변경 후에도 같다면 자동 OCR 개선을 PASS로 기록하지 않는다. 독립 정답이 없다면 PRECISION_ADVANTAGE=UNVERIFIED_DATA, 측정 자료에서 이득이 없으면 NO_GAIN이라고 적는다. 기능 PASS와 자동 정확도 우위 인증을 분리한다. `CER≤1%`는 장기 목표이지 테스트를 조작해 맞출 출시 숫자가 아니다.

### 4.3 OCR 실행·운영 안전
- 일반/고정밀 실제 추론 경로 차이와 모드별 jobId·모델/캐시 키 기록; 동일 파일을 두 모드로 실행해도 잘못된 모드 캐시를 사용하지 않음
- OCR 검수·초안 수정·원문 대조·확정 불변 판본·S4 분석 참조·저장/재조회·UTF-8 TXT/구조 JSON export
- 취소·재시도·중단 후 페이지별 재개, 오래된 작업 고립, 원본 파일/파생 이미지 안전 삭제 경계
- 초회 OCR 102.6초 예외에 대하여 큐 대기·모델 로드·렌더·추론·DB 저장의 단계별 관측으로 원인 확인. 설명 없는 재발이 실제 사용 불가능을 초래하면 수정
- 모델 로컬 설치 파일 및 가중치·라이선스 고지, 오프라인 동작, CPU/메모리 입장, 7.8GiB 수준의 VL 별도 메모리 요구 고려
- 코드/파생 캐시만 임의 복구 자료로 간주하지 않음. 원본 PDF·확정 판본과 접근 통제의 백업 범위를 확인

## 5. STAGING 제품 전체 검증 매트릭스 — 운영 중지 전에 수행

STAGING은 `STAGING` 프로필과 격리 DB·업로드·로그·세션·백업을 사용한다. 운영 계정·DB·비밀값·글을 복사하거나 운영에 proxy하지 않는다. 기존 합성 계정(A/B)과 테스트 파일을 재사용한다. 기존 시험 데이터를 무단 초기화하지 않는다.

아래 **현재 구현된 제품 기능**을 모두 직접 실행한 테스트 또는 hash·환경 바인딩이 유효한 검사 증거에 연결한다. 빠진 항목이 있으면 해당 기능을 실제 검증하고 해당 테스트를 만든다. 테스트 이름만 있어도 의미적 assertion이 없으면 PASS로 하지 않는다.

A. **인증·개인정보·권한**: 로그인/로그아웃, 기존 Google 운영 결합(실계정 필요 여부 분리), 동의·탈퇴·삭제 정책, 비인가 401/403, IDOR·CSRF, 개인 간 글/파일/분석/메모 격리, 관리자 권한 우회 금지.
B. **글쓰기·분석**: 글 생성·자동저장·수정·버전·재조회·기존 분석·질문·STALE, S4 R0/R1·근거와 주장 표시, 허위 관계 차단, 긴 글·세 화면 폭/두 테마.
C. **자료실·관리**: 개인/공용 목록·검색/선택, 관리자 자기 자료의 공용 전환·공개 중지, 권리 불명/복수 판본 차단, 전환 후 다른 사용자의 분석, 공개 중지 후 작성자의 기존 분석 조회, revision·첨부·quote/rubric과 권한.
D. **OCR 통합**: 텍스트/스캔/혼합 PDF, 일반·고정밀 모드, 선택 모달 X·ESC·초점 복원, 실모델 추론/중복·캐시, 구조/오류 검수, 국소 재인식·VL, 취소·재개, 확정·내보내기·S4 재조회.
E. **원문 보호·문서 출력**: MATCH_ONLY 검색/조회/다운로드/PDF/페이지 크롭/원시 OCR 및 대안 노출 차단, VIEW·DOWNLOAD 구분, TXT/JSON/인용·문서/분석 출력의 개인 권한.
F. **웹 화면·탐색**: SPA 직접 URL과 새로고침, 두 테마, 1440/820/390px, 메뉴·패널·모달·ESC 한 단계 뒤로 가기, 키보드·저장 실패 보호, 주요 브라우저 콘솔 오류·가로 넘침. 실제 수정 대상 화면의 테마 직접진입 문제가 재현되면 기능적 영향에 맞게 수정한다.
G. **서비스·자원**: 로컬/외부 HTTPS, API·정적 파일의 동일 서비스 출처, 서버 중지/시작, 작업 실패·중복 실행·메모리 가드, 운영/시험 분리, C 로컬 백업·외장 예약 작업 정의가 이번 변경으로 훼손되지 않음.

이미 구현된 것인지 불명확한 기능은 먼저 실제 코드·route를 확인한다. **차기 1.2.0 계획만 있고 구현되지 않은 E01/E03/E05, D07~D14 등을 새 배포 요구로 자동 추가하지 않는다.** STAGING의 자동 인증 경로(`/__staging__/session/...`)는 오직 테스트 환경에서만 허용하고 운영 빌드·운영 라우트에서 반드시 거부/부재를 검사한다.

실행 순서는 오류와 연결된 단위 테스트 → 영향받는 관련 suite → 최종 후보의 모든 변경 영향 테스트 → 마지막 통합 테스트·타입검사·production build·실제 STAGING API/DOM·S4/OCR 성능·자료 보존 검사다. 이미 완료된 변경불변 검사 재사용은 허용하되 제품·의존성·테스트 입력이 달라졌다면 실제 재실행한다. 보고 시 reused/reexecuted를 구분한다.

**STAGING 전체 Gate**: 제품 인벤토리의 주요 사용 흐름 100%가 PASS이고 설명되지 않은 핵심 FAIL/UNVERIFIED가 0이어야 운영 적용에 진입한다. 테스트 프레임워크가 미검사를 성공으로 반환하거나 임의 skip/xfail이 추가되지 않도록 한다. 모바일 실기기·실제 문학 독립 정확도 등 테스트 환경에서 검증할 수 없는 비핵심/평가 항목은 솔직하게 UNVERIFIED로 남기며 사용자 지인 시험이라는 범위 내 출시 판단과 구분한다. 실제 인증·개인정보·데이터 격리·원문 노출·저장·복귀 같은 필수 안전 항목이 미검증이면 배포 전 중단한다.

## 6. 운영 중지 전 Release Gate — 전부 PASS일 때만 진입

1. 제품 인벤토리에 포함된 모든 현재 구현된 주요 기능의 STAGING 검증 PASS. 우회된/미검사된 필수 보안·데이터 경계 없음.
2. S4 엔진 계약·기준 관계·실제 속도·저장·조회·권한 성능 PASS, 현재 활성 분석 경로 확인. 분리된 실제 의미 정확도 인증은 실자료 없으면 UNVERIFIED.
3. OCR 일반·고정밀 기능·모델 바인딩·검수·확정·S4 연결 PASS. 품질 우위/1% 목표는 실제 자료 없으면 별도 UNVERIFIED로 유지; 합성 동일 CER를 정확도 개선 PASS로 표시하지 않음. 심각한 원문 누락·잘못된 자동 교정·고갈·OOM 문제 없음.
4. 최신 배포 delta에 대해 경로별 충돌 해결과 런타임 의존성 SHA 검증. 운영의 S4·기존 사용자 글·관리자 자료·외장 백업·로그인/DPAPI·자료 보관 설정을 훼손하지 않음.
5. STAGING 전용 라우트/데이터/세션·개발 비밀값의 운영 누출 0, 기본권한·IDOR·CSRF·MATCH_ONLY·PDF/다운로드 안전 PASS.
6. 운영 DB의 schema/파일/업로드 상태와 예정 후보의 호환성 확인, 현재 읽기/쓰기 작업 드레인 가능성 확인. **운영 DB를 초기화·이전할 필요가 없는 delta를 우선**. 새 schema가 필요하면 운영 DB 복사본에서 공식 migration/무손실 복원을 검증하고 해당 변경의 승인 권한을 먼저 확인한다. 데이터 삭제·파괴적 migration은 이 지시의 허용 범위가 아니다. 운영 원본에는 사전 합의 없는 migration을 실행하지 않는다.
7. 운영 C:에 새 암호화 백업을 기존 백업 도구의 안전한 방식으로 생성하고, 격리 복원·무결성·FK·schema·업로드 참조를 확인. 코드/빌드/OCR 모델 설정/이전 release binding의 복귀 사본과 각각의 SHA·manifest 생성. 과거 영수증 없는 백업을 새 근거로 승격하지 않음. E: Warning이나 과거 exit1의 오류를 숨기지 않되 C의 확인된 백업을 보존.
8. 기존 공식 소유권·lifecycle lock, PID 및 서비스/터널 재시작 절차 확인. 서버 정지·복원·재기동에 필요한 모든 파일과 명령을 준비. 운영 유휴/쓰기 중지 시점 전까지 원래 서비스 계속 가동.

이 지시는 위 Gate를 전부 만족한 검증 후보에 대한 **계획된 단일 운영 배포 및 서버 stop/start를 승인**한다. 인증된 실제 운영 계정이 없어 필수 인증 경로를 시험할 수 없는 경우 먼저 현재 운영 로그인 코드·설정과 보존된 실제 Google 로그인 영수증의 해시 유효성을 확인하고, 중요한 인증 위험을 배제할 증거가 없으면 배포 전 USER_ACTION_REQUIRED로 멈춘다. 운영에 시험용 세션 라우트를 새로 만들어서는 안 된다. 불필요한 중간 승인 요청 없이 진행한다. FAIL이 남으면 운영 서비스는 그대로 둔 채 해당 코드/테스트를 같은 작업 안에서 고쳐 재검증한다. 핵심 필수 항목을 여전히 검증할 수 없다면 운영을 중지하지 않고 BLOCKED/USER_ACTION_REQUIRED로 종료한다. 시간 경과만으로 Gate를 면제하거나 테스트 기대값·로그를 고쳐 PASS를 만들지 않는다.

## 7. 실제 운영 서비스 중지 → 적용 → 재시작

**이 단계 전까지 운영 서버·터널을 중지하지 않는다.** 운영 중 데이터 변경과 예약 작업이 겹치지 않게 기존 lifecycle lock과 저장 잠금을 사용한다.

1. 현재 실행 코드/배포 manifest·서비스 소유 PID·실행 URL·DB 루트/스키마 확인. 최종 적용 직전 쓰기 입장 중단, 들어온 요청과 OCR/S4 작업 드레인 또는 안전 체크포인트 저장. 새 데이터 유실 가능성이 남으면 중지 전 BLOCKED.
2. 가능하면 기존 `backend/network_service.py stop --operating`의 공식 구현을 사용해 **운영 서버와 해당 owned 터널만** 종료. 다른 Python/Waitress·STAGING·Windows 사용자 작업·무관한 터널은 종료하지 않는다. 정확한 소유 PID가 종료됐는지 확인. 예시 명령은 실제 cwd/venv 확인 후 실행:
   `.venv\Scripts\python.exe backend\network_service.py stop --operating`
3. 서비스 중단이 확인된 상태에서 DB의 신규 쓰기가 없는지 확인한다. 사전 백업 이후 마지막으로 작성된 데이터가 있으면 기존 안전한 백업 도구로 **중단 직전 기준의 최종 백업을 갱신**하고 격리 복원·무결성 검사를 확인한다. 새 백업을 만들 수 없거나 복원에 실패하면 파일 교체를 하지 않고 기존 버전으로 서비스를 다시 연다. 운영 DB·파일·세션을 보존하고 과거 백업으로 되돌리지 않는다. 기존 schema 유지가 가능하면 migration 없이 코드/정적 빌드/허용된 OCR 설정만 적용한다.
4. manifest에 등록된 검증 delta만 안전한 staging→운영 파일 적용 절차로 복사한다. 파일별 before/after SHA, 경로·소유권·파일 충돌을 검사한다. API·OCR·S4 런타임·프론트엔드 dist, 인용·자료실·사용자 글 소비자까지 실제 관련 파일을 빠짐없이 포함한다. HTML entrypoint는 기존 방식대로 마지막에 적용한다. 운영 설정 중 DPAPI 비밀·OAuth·ngrok 주소·관리자 설정·개인정보 보관·외장 백업/60분 예약 작업은 변경하지 않는다.
5. 최신 `OCR_LOCAL_CONFIG` 바인딩·venv·모델·Tesseract exe/언어데이터·가중치 SHA·프로세스 메모리 예산을 반영하고 프로덕션 runtime에서만 허용한다. 모델 파일을 임의 인터넷 다운로드하지 않고 별도 성능 호스트의 모델을 운영에 무검증 복사하지 않는다.
6. 적용한 모든 운영 파일의 해시와 후보 manifest를 다시 읽어 대조한다. old release code/build/config 복귀 사본을 유지한다.
7. 공식 `.venv\Scripts\python.exe backend\network_service.py start --operating`을 사용해 **운영 서비스를 다시 시작**한다. owned 프로세스·터널·기존 HTTPS URL·health·재시작 정상 여부를 확인한다. 임시 STAGING URL이나 테스트 비밀을 운영 URL로 전환하지 않는다.
8. 운영 서비스가 열린 뒤에도 예약 작업과 C·E 백업 경로가 바뀌지 않았고 비인증 접근이 보호되며 동일 로그인·세션 정책을 유지하는지 확인한다. 이 단계를 수행했다고 사용자 계정의 신규 분석까지 자동 확인됐다고 간주하지 않는다.

### 배포 오류 발생 시
- 새 릴리스의 시작/기본 기능이 실패하면 운영 DB는 **그대로 보존**하면서 검증된 이전 소스·빌드·설정으로 코드 복귀를 시도하고 가능한 경우 **이전 안정 운영 서버를 재개방**한다.
- 배포 이후 새 OCR 작업·확정 판본·분석이 생성돼 이전 리더가 처리할 수 없는 경우 이전 코드/DB를 무조건 복구하지 않는다. 새 데이터와 호환성을 검사하고 데이터 보존을 우선한다. 필요한 경우 신규 OCR 실행만 안전하게 중단하고 기존 글쓰기·분석 기능을 살리는 제한된 복구를 수행한다.
- 이전 릴리스도 안전하게 시작할 수 없으면 운영 DB/파일/로그를 보존하고 추가 변경 없이 안전한 중지 상태를 보고한다. 허가 없는 데이터 삭제·불가역 복구로 억지로 health=200을 만들지 않는다.
- 사고가 나도 다른 작업·사람의 서버를 일괄 종료하거나 인증/권한을 약화하지 않는다.

## 8. 재시작 후 실제 운영 검증 및 마감

서비스 재시작 후 실제 `owned` 프로세스가 새 검증 코드·OCR 설정으로 실행되는지 파일 SHA·모델 버전·PID·HTTP와 라우트로 확인한다.

- 기존 사용자 로그인/로그아웃·세션(가용한 실제 인증 세션 사용, Google 우회/QA 세션 사용 금지), 개인정보 동의 정책, 관리자 전환·공개 중지, 자료·PDF·글·분석 재조회
- 신규 에세이에서 S4 분석 ID/글 버전/엔진 정보 생성·저장·조회, 주석·STALE/질문 및 승인/REVIEW 관계
- 원문 텍스트 PDF, 일반·고정밀 OCR 스캔 파일의 서로 다른 job ID·mode·캐시 경로, 검수·확정 리비전·S4 연결 결과, MATCH_ONLY 비노출
- 사용자 요청 취소, 오류 메시지, 기본 화면·책 화면·자료실, light/dark·데스크톱/좁은 너비의 기본 경로
- C: 백업 정책·외장 E: 지정 볼륨/GeulbitExternalBackupCopy(기존 Warning 표시는 보존), 실행한 서버·터널이 이번 owned 서비스인지 확인

실제 운영 시험은 기존 사용자의 **허용된 시험 계정·합성 자료**로만 실시한다. 기존 개인 글·실제 원작품을 변경하지 않는다. 사용자의 로그인 세션에 접근할 수 없으면 세션을 조작하거나 완료한 척하지 말고 필요한 최소 사용자 조작을 한 번에 요청한다. 실제 새 분석/OCR 저장기록이 확인되지 않으면 해당 `POST_DEPLOY_SMOKE=USER_ACTION_REQUIRED`로 두고 전체 결과와 구분한다. 서비스는 필수 안전 검사에 문제가 없다면 정상 운영 상태로 유지한다.

새로 생긴 운영 데이터를 rollback으로 무단 삭제하지 않으며 release manifest, before/after 해시, 실제 backend 프로세스·OCR runtime binding, 적용·복귀 명령·검증 결과를 별도 Handoff/receipt에 기록한다. 사용자 개인정보·실제 원문·비밀/세션 쿠키는 첨부하지 않는다.

## 9. 합격 조건과 최종 보고

상태를 반드시 분리하여 보고한다.
- `S4_IMPLEMENTATION` / `S4_PERFORMANCE` / `PRIMARY_ANALYSIS_ENGINE`
- `OCR_IMPLEMENTATION` / `PRECISION_ADVANTAGE` / `RESOURCE_SAFETY`
- `STAGING_FULL_REGRESSION` / `STAGING_DATA_ISOLATION`
- `RELEASE_GATE` / `OPERATING_APPLIED` / `OPERATING_SERVICE_REOPENED`
- `POST_DEPLOY_S4` / `POST_DEPLOY_OCR` / `DATA_BACKUP_PRESERVED`

**최종 성공**은 (a) 기존 S4 및 OCR 필수 기능 모두 정상, (b) STAGING 인벤토리의 필수 사용 흐름 통과, (c) 새 코드·설정의 실제 운영 적용·서비스 재기동·핵심 안전 점검 PASS, (d) 기존 데이터·권한·백업 보존, (e) 실제 사용자 기반 분석/OCR 기록 또는 그 항목에만 명시한 사용자 작업 상태가 정확하게 구분된 것이다.

실제 문학 평가자료 미확보는 `PRECISION_ADVANTAGE=UNVERIFIED_DATA`로 두며 지인 시험용 운영 배포 자체를 부당하게 막는 Gate로 바꾸지 않는다. 그러나 정확도 우위나 S4 의미적 정확도가 인증됐다고 적지 않는다. 원문 누출·권한 우회·데이터 손실·서비스 반복 종료·설명되지 않은 승인 관계 회귀가 남으면 RELEASE_GATE=BLOCKED로 유지하고 운영 적용 전 중단한다.

최종 보고는 **STATUS / CHANGED / RULES / TESTED / RISKS** 다섯 항목만 간결하게 작성한다.
- STATUS: 위 상태값과 운영 URL/서비스 열림 여부, 오류 때 복구 상황
- CHANGED: 제품 파일/엔진/빌드/OCR 설정의 실제 적용 SHA와 테스트 전용 파일 제외 증빙
- RULES: 이전 schema·원본/불변 판본·소유권·MATCH_ONLY·S4·R2 off·백업/예약/인증 보존
- TESTED: 명령, exit code, 통과 수, 기존 receipt 재사용과 실제 새 검증 구분, STAGING 전체 매트릭스, 실제 운영 분석/OCR ID·모드
- RISKS: 미측정 실자료 정확도, 지연/메모리/모바일/라이선스, 인증 사용자 행동 필요 여부, 복구 제약

장시간 작업이 도구 실행 제한 등으로 중단되면 기존 단일 PATCH ID의 짧은 checkpoint(후보 SHA, 완료 Gate, 실행한 명령·exitCode, 미완료 항목, 다음 정확한 명령)로 재개한다. 별도 새 Phase나 복구 Runner를 만들지 않는다. 성공하면 해당 단일 작업을 종료한다. 다른 UI·원작품 글쓰기의 차기 1.2.0 기능, R2 활성화, 무관한 자동화·리팩터링·장문 보고 생성으로 확대하지 않는다.
