# 글빛 V2.2 S4 — 잔여 역할 누락 보완과 배포 후보 기술 검증

## 목표와 기준

S3 PASS_IMPLEMENTATION을 완료 상태로 고정한다. 확인된 N03/N08/D03의 역할 누락 6개를 같은 작업 단위에서 보완하고 최종 후보만 통합 검증한다. 새 의미 분석, R2 활성화, 운영 배포는 하지 않는다.

AGENTS.md, 최신 Active Plan, S3 최종 PASS receipt, S2의 source-map-v2.json과 condition-details-v2.json 중 세 에세이 항목, 기존 합성24 실행 계약만 참조한다. 이미 끝낸 진단·Runner 개발·S3 보완을 반복하지 않는다.

출발점은 정식 제출된 S3다.
structure.py SHA-256:
9464b0e520ed4e87d540c04ba67d1267b49f3f73e6c656f4fa0c599ecad2dfdd
S3 44개, 기존 보호 93개, 57조건·승인16쌍의 PASS receipt를 기준으로 삼는다. HEAD만으로 상태를 확인하지 말고 최신 source snapshot과 승인 변경분을 대조한다.

이번 입력 해시는 출발점 검증용이다. S4에서 승인된 구조 코드 변경의 새 해시는 별도 기록한다. 기존 Golden/Baseline이나 원본 실패 증거를 재기준화하지 않는다.

기존 Runner의 별도 Queue/approval 등록 방식을 사용한다. 신규 계약·후보·기대조건·검사 스크립트·결과·빌드 산출물·Checkpoint/Handoff는 기존 글빛 Runner 출력 루트의 새 S4 디렉터리에만 만든다. 소스 Scope와 실행 산출물 Scope를 구분한다.

관련 symbol → 정의 → 호출부 → 필요한 범위 → 테스트 순서로만 탐색한다. 실제 경로·명령·환경을 확인한 뒤 시작한다. 범위를 벗어난 구현이 필요하면 이를 자동 확대하지 않는다.

## 2. 구현 전에 기대조건을 확정한다

아래 대상은 독립 정답이 아니라 이미 분석한 합성 개발 기대조건이다. S3 기준 결과와 실제 Kiwi 토큰을 필요한 문장에서만 확인한다.

| 대상 | 필요한 역할 | 이미 확인한 누락 조건 |
| N03 sentence-3 | CLAIM_CANDIDATE | ‘보여준다’가 검출돼도 ‘비극’이 유한 명사 필터 밖이라 제거됨 |
| N03 sentence-2 | EVIDENCE_CANDIDATE | ‘아내는 이미 숨져 있다’의 문학적 인물 문맥·사건 상태가 누락됨 |
| N08 sentence-1 | CLAIM_CANDIDATE | ‘나온다고 볼 수 있다’ 해석 서술 형식 누락 |
| N08 sentence-2 | EVIDENCE_CANDIDATE | 동이가 허 생원을 ‘업어 건너게 하는’ 장면의 행동 단서 누락 |
| D03 sentence-1 | EVIDENCE_CANDIDATE | ‘매장을 금지한다’의 금지+하/XSV 누락 |
| D03 sentence-2 | EVIDENCE_CANDIDATE | ‘명령을 어기고 … 의무를 행한다’의 행동 단서 누락 |

각 목표에 해당 역할이 추가되되 기존 역할·다른 단서·문장 ID·코드포인트 span은 보존해야 한다. CLAIM/EVIDENCE는 배타적이지 않다. 기존 역할이 있는 문장에 CLAIM-only 또는 EVIDENCE-only를 요구하지 않는다.

음성 독서·문자 처리, 화면 정보의 ‘보여준다’, 단순 지각·가시성의 ‘볼 수 있다’, 작문 지시·일반 규범의 ‘금지한다’, 가정·희망·인용된 주장, 추상적 책임을 나누는 태도 등을 구별하는 최소 대조를 고정한다. 부정문·인용문은 모두 역할 없음이라는 전역 규칙으로 처리하지 않는다.

특히 신규 CLAIM cue를 주지 않는 검사와 모든 기존 역할을 지우는 검사를 구분한다. 기존 EVIDENCE 보존과 새 주장 기대조건의 충돌을 코드 수정 전에 확인한다. S3 반례 A/B와 기존 44개 기대조건은 변경하지 않는다.

원래 문장·기대조건·정규화 본문 해시·원본 역할·추가할 역할·금지할 신규 cue를 기록한다. 후보 출력을 정답으로 복사하지 않는다. 계약 오류가 발견돼도 조용히 수정하거나 Golden을 바꾸지 않는다.

## 3. 같은 후보에서 여섯 역할을 최소 보완한다

analyze_structure의 기존 역할 후보 생성 구조를 재사용한다.

- 명시적 해석 서술과 그 대상의 연결을 확인한다. ‘비극’ 등 명사가 문장 어디에나 있다는 조건이나 ‘볼 수 있다’ 부분 문자열만으로 CLAIM을 부여하지 않는다.
- 작품 문맥 속 인물의 구체적인 사건·행동·상태 보고를 식별한다. 모든 VV/XSV를 근거로 승격하거나 앞 문단의 인물을 문서 전체에 전파하지 않는다.
- 작품명·문장 ID·에세이 전체 문장을 하드코딩하지 않는다. 새 일반 의미 사전·파서·병렬 역할 엔진을 만들지 않는다.
- 공용 ACTION_LEMMAS는 R1 사건 수 계산에도 사용된다. 목록만 무조건 확장하지 말고 후보 역할과 R1 판단에 미치는 영향을 확인한다. R1 승인·복수 사건·경쟁·원거리 지시 규칙 자체는 변경하지 않는다.
- 기존 역할, 점수 가중치·임계값·margin, 출처 충돌 정책, 질문 정책, 표시·스냅샷 계약을 유지한다. 역할별 관찰 단서 수의 정당한 증가는 기존 계산 방식으로만 반영한다.
- S3의 해석 보어 범위와 독서 절차 오탐 방지는 유지한다. 다른 기능의 임의 정리는 하지 않는다.

관계 생성은 기존 엔진에 맡긴다. 역할 6개 복구를 관계 6개 자동 승인으로 바꾸지 않는다.

관계 안전성:
- P06/D01의 기존 REVIEW를 화살표를 늘리기 위해 승인으로 바꾸지 않는다.
- D03은 두 선행 사건과 ‘이 선택’의 모호성을 억지로 해소하지 않는다. 이번 범위에서 R1 지시어 목록도 확대하지 않는다.
- N08의 무관한 교차 작품 관계를 승인하거나 확정적인 질문에 사용하지 않는다. 실제 출처 판정 도달 여부를 기록한다. 아직 검색되지 않았다면 NOT_REACHED이지 출처 차단 PASS가 아니다.
- N07/P08 정상 비교, ‘에서는’ 인식, ‘비교적’ 오탐 방지는 보존한다.

같은 후보 안에서 관련 실패를 수정하되 후보 보완은 최대 2사이클이다. 횟수와 실패를 기록한다. 단계마다 새 recovery 체인을 만들지 않는다. 독립 검토 전 검증된 후보만 정식 제출한다.

## 4. 기능 검증 — 최종 후보에서 묶어서 수행한다

실패한 최소 테스트부터 실행하고 통과 후 아래로 확장한다.

1) 신규 역할·대조 테스트 전체, S3 44개, 보호 93개.
기존 테스트 수정·skip·xfail 금지. 기존 31/44/93과 신규 개수를 구분하며 중복 실행 횟수를 고유 테스트 수로 더하지 않는다.

2) 기존 57조건을 1회 재생한다.
승인16쌍 손실0, 설명되지 않은 역할·관계·질문 회귀0, 동결된 평가 기준의 기존 승인 Precision/Recall 회귀0을 확인한다.

3) 합성24 전체를 기존 실행 도구로 한 번 재평가한다.
STANDALONE·DECLARED_TITLE_FIXTURE에서 각 2회로 결정성을 확인하되 이후 소스 불변이면 반복하지 않는다. R2 호출이 선택 가능하면 제외한다. 기존 도구가 진단 전용 섀도 호출을 포함하면 도구를 고치지 않고 기존 지원 입력에서만 그대로 실행하며 결과는 참고로 분리한다. 운영 R2는 계속 DISABLED다.

에세이별 역할·관계·질문·표시·미검색 이유를 S3 또는 직전 검증 결과와 비교한다. 새 정답 라벨이 없으므로 신규24의 Precision/Recall은 N/A다. 신규 주장 수나 REVIEW 수 증가를 정확도 향상이라고 보고하지 않는다. 사전 고정 개발 기대조건과 기존 Golden 지표를 분리한다.

4) 같은 후보 해시로 독립 Read-only Review와 Scope·보호28·고정39 검사를 수행한다. G5의 기존 WAIVED_BY_USER를 PASS로 바꾸거나 별도 Claude 검토를 새 필수 조건으로 추가하지 않는다.

기능 완료 조건:
- 여섯 목표 역할이 두 모드에서 모두 복구됨.
- 사전 대조 및 기존44·93 PASS.
- 기존57조건·승인16쌍 보존.
- 새 잘못된 승인·확정 질문, 정상 비교의 설명되지 않은 손실 0.
- 모든 합성24 결과가 기록되며 미검색·미측정·미지원이 PASS로 숨겨지지 않음.

도달하지 않은 관계 정책이나 범위 밖 누락은 잔여 제한으로 기록한다. 안전성 회귀가 발생하면 정식 반영·다음 검증으로 전진하지 않는다. 기능 조건이 통과해도 일반 정확도 승인으로 해석하지 않는다.

## 5. 배포 후보 기술 검증 — 코드 동결 후 1회

기능 조건이 통과한 동일 후보에서만 시행한다. 인적 데이터가 없어도 기술 검증은 진행할 수 있으나 메인 Phase4A/4B 완료로 기록하지 않는다.

- 기존 명령의 typecheck, lint(설정된 경우), production build를 1회 수행한다. 실패해도 이번 Scope 밖 UI·빌드 설정을 수정하지 않는다.
- 기존 격리 HTTP/브라우저 검증 스크립트를 사용한다. 분석→저장→재조회, 이전 스냅샷, 로그인·소유권·CSRF, 승인 화살표 방향·위치, REVIEW의 확정 화살표 제외, 질문 표시, Unicode를 확인한다.
- 기존 모바일 viewport/터치 자동검사는 실행 가능할 때 수행한다. 에뮬레이션과 실제 기기 검증을 구분한다. 미실행을 PASS로 표시하지 않는다.
- MATCH_ONLY 보호는 기존 권한 fixture로 검사한다. 실제 원작품·판본이 없는 합성 제목 fixture를 인용 정확도 검증으로 보고하지 않는다.
- 모든 HTTP/브라우저 쓰기는 이번에 만든 임시 DB·격리 서버에만 허용한다. 운영 DB·운영 서버 접근·재시작은 금지한다. 기존 운영 로그·개인정보·비밀값을 패키지에 넣지 않는다.

성능:
동일 하드웨어·입력·판본/fixture·의존성으로 S3 기준과 S4를 비교한다. 30,000자 입력과 원작품0/1/복수 조건의 기존 측정 계약을 재사용한다. 프로토콜이 없으면 각 조건에서 warm-up3회와 측정30회를 각각 수행하고 표본 수와 일회성 Kiwi 초기화를 별도 기록한다.
p50/p95를 계산하고 신규p95 <= 기준p95×1.5를 검사한다. fixture 메타데이터만 사용했다면 실제 원문 대조 성능은 NOT_MEASURED다. 반복 문장 합성 부하를 독립 문학 평가로 세지 않는다. 30분 soak test나 새 성능 플랫폼은 만들지 않는다.

실행 환경이나 기존 스크립트가 없으면 NOT_RUN/BLOCKED_VALIDATION과 정확한 이유만 기록한다. 새 배포 시스템·브라우저 자동화 체계를 구현하지 않는다.

## 6. 산출물과 상태

기존 Runner 최종화로 별도 S4 Checkpoint·Handoff를 만든다. 정식 개발 worktree 반영은 기존 S4 Scope·검증 조건을 모두 통과한 정확한 후보에만 허용한다. 이전 S3 receipt/소스/실패 이력은 보존한다. 운영 배포는 하지 않는다.

산출물은 핵심 patch·해시, 여섯 역할 전후표, 합성24 결과, 기존57 비교, 기술 검증 명령/exit/count, 빌드 결과 참조, 남은 정확도·데이터·환경 제한과 기존 절차를 인용한 rollback/runbook으로 제한한다. 보고서는 최종에 한 번만 작성한다.

상태를 나눈다.
- IMPLEMENTATION: PASS 또는 BLOCKED_REGRESSION/VALIDATION
- TECHNICAL_PREP: READY 또는 BLOCKED_VALIDATION/NOT_RUN
- ACCURACY_CERTIFICATION: BLOCKED_DATA
- DEPLOYMENT_AUTHORIZED: false

TECHNICAL_PREP READY는 측정된 기술 검증 완료만 뜻한다. 독립 인적 평가, 최종 홀드아웃, 미검증 원작품 조건과 별도 배포 승인을 대신하지 않는다. Gate 미통과를 이유 없이 waive하지 않는다. R2는 활성화하지 않는다.

## 공통 금지와 종료

이미 완료된 Phase 재구현, Runner 엔진 변경, 범위 밖 리팩터링, 테스트 기대값의 사후 완화, 인적 라벨·권한 증빙 위조, Golden/Baseline 수정, 새 AI API, commit/push/merge/deploy 금지.

기존 완료 조건을 바꾸지 않는다. Phase4A BLOCKED_DATA, R2 DISABLED, 메인 Phase4B NOT_STARTED를 유지한다. 이번 기술 검증 결과는 향후 Phase4B에서 후보·환경 동일성 확인 후 재사용할 수 있도록 묶는다.
