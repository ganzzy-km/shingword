# PATCH-STAGING-001 — 운영과 분리된 로컬 테스트 환경 구축

## 목표와 승인

운영 중인 글빛을 중지하거나 변경하지 않고 별도의 테스트 서버·DB·자료 저장소를 구성한다. 구현뿐 아니라 테스트 환경의 초기화, 기동, 새 분석 저장·재조회, 중지·재기동까지 확인하고 사용 가능한 상태로 마무리한다.

이번 요청은 테스트 전용 디렉터리·설정·DB 생성, 합성 계정·자료 생성, 로컬 테스트 프로세스 실행과 필요한 관련 코드·테스트의 최소 수정을 승인한다. 운영 적용·운영 DB migration·공개 터널·예약 작업 변경은 승인하지 않는다.

AGENTS.md와 docs/automation/ACCEPTANCE.md의 패치 원칙, PATCH-ENGINE-001 적용 기록, PATCH-BACKUP-001의 최신 application-receipt 및 복귀 기록에서 필요한 항목만 확인한다. 이미 완료한 Phase를 재개발하지 않는다.

## 1. 출발점과 보존 대상

- 운영 데이터 루트: C:\Users\USER\GeulbitData
- 운영 DB: C:\Users\USER\GeulbitData\db\geulbit.sqlite3
- 운영 스키마: 0004_user_annotations
- 운영 엔진: 적용된 S4. structure.py 기준 SHA는 0ffebe4ad0121f488185d2fcba82fdcf17bc16f3a82ca03a03d6f712b9f84696이며 최신 적용 receipt와 대조한다.
- 외장 백업: E:\GeulbitBackups, 기존 고정 볼륨 설정 유지
- GeulbitExternalBackupCopy: 60분 활성 상태 유지
- 기존 로컬 백업: 24시간 생성·7일 보존 유지
- 테스트 루트: C:\Users\USER\GeulbitStagingData
- 테스트 DB: C:\Users\USER\GeulbitStagingData\db\geulbit.sqlite3

기준은 과거 S4 snapshot 단독이 아니라 S4 운영 적용과 PATCH-BACKUP-001 적용 delta가 모두 설명되는 현재 상태다. 과거 개발본으로 운영 파일이나 백업 설정을 덮어쓰지 않는다.

S4의 실제 계정 새 분석 확인은 별도 USER_ACTION_REQUIRED로 유지한다. 그 기록 부재, 인적 정확도 라벨 부족, E:의 기존 Warning이나 영수증 없는 백업 제외는 이 테스트 환경 구축의 선행 차단 조건이 아니다.

## 2. 최소 탐색과 Scope

관련 symbol → 정의 → 호출부 → 관련 테스트 순으로만 조사한다. 기존 설정·데이터 루트 해석, Flask 앱 생성, 로컬 실행, QA 인증·합성 fixture, DB 초기화 경로를 확인한다. backend/app/config.py, backend/app/storage.py, backend/app/__init__.py와 backend/v2_tests의 기존 실행·fixture는 위치 확인의 출발점일 뿐 전부 수정하는 목록이 아니다.

변경 범위는 테스트 프로필·설정/로컬 실행 진입점, 필요한 경로·세션·작업 namespace 분리, 관련 targeted test와 짧은 사용 안내다. 기존 기능을 우선 재사용한다. 전체 앱·인증기·백업기·분석기를 복제하지 않는다.

실제 필요한 파일 경로와 실행 산출물 위치를 한 번 확정해 기존 패치 계약에 등록한다. 이 명세는 위 기능 범위의 구체적인 목록을 최초 등록하는 작업을 승인한다. 의미 없는 고정 파일 수를 맞추기 위해 복제 파일이나 우회 코드를 만들지 않는다. 기능 범위 밖 변경이나 보호 파일 개정이 필요하면 해당 최소 사유만 보고한다.

수정은 운영 경로와 분리된 개발본에만 수행한다. 기존 검증된 격리 작업본을 재사용하되 운영 0004 호환 adapter와 승인 delta를 확인한다. 필요 시 manifest에 해당하는 소스·빌드만 별도 테스트 실행 위치에 복사한다. 운영 폴더 전체를 복사하여 DB·업로드·비밀값을 함께 가져오지 않는다.

실행 증거와 별도 Checkpoint는 기존 Runner output 아래 PATCH-STAGING-001 전용 위치에 추가한다. 기존 Runner, 운영 Queue, 과거 receipt와 snapshot은 재작성하지 않는다.

## 3. 데이터 경로 분리

STAGING이라는 명시적인 프로필로만 시작한다. 프로세스 전용 설정을 주입하고 운영 .env, 사용자 전역 환경변수, 레지스트리, 운영 release binding을 변경하지 않는다.

DB뿐 아니라 업로드, 추출 텍스트, 임시 파일, 캐시, 로그, 세션·비밀값 저장소, 로컬 테스트 백업, PID·잠금·작업 상태 경로를 테스트 전용 위치로 분리한다. 기존 폴더 구조를 재사용한다.

DB 연결·폴더 생성·초기화보다 먼저 실제 경로를 검증한다.
- 프로필이나 필수 경로 누락 시 운영 기본값으로 되돌아가지 말고 명확히 실패한다.
- 운영 루트와 같거나 포함 관계인 경로, E:\GeulbitBackups 및 기존 운영 백업 경로는 테스트 쓰기 대상으로 거부한다.
- Windows 경로 정규화·대소문자·junction/심볼릭 링크·재분석 지점을 고려한다. DB 하드링크 등으로 동일 운영 파일을 가리키는 경우도 거부한다.
- 잘못된 경로 차단 검사는 임시 폴더의 모의 운영 경로로 수행한다. 실제 운영 DB를 쓰기 모드로 열어 차단 여부를 시험하지 않는다.

테스트 루트가 없으면 생성한다. 기존 내용이 있으면 먼저 소유 표식·프로필·스키마를 확인한다. 모르는 파일이 있다고 삭제·초기화하지 않는다. 재실행은 기존 staging 데이터를 보존해야 한다.

기존 빈 DB 초기화·migration 도구로 새 테스트 DB만 0004_user_annotations까지 구성한다. 개발 저장소의 최신 head인 0005를 자동 적용하지 않는다. 운영 DB·암호화 백업을 복사·복원하여 테스트 DB를 만들지 않는다. 운영과 다른 스키마가 필요한 기능 개발은 이번 범위가 아니다.

## 4. 실행·인증·백업 격리

- 테스트 서버는 loopback에만 바인딩한다. 사용 가능한 별도 포트를 확인하고 테스트 설정에 고정한다. 운영 포트가 점유됐다고 운영 프로세스를 종료하지 않는다.
- 테스트 프론트엔드가 실제로 staging API를 사용하도록 확인한다. 고정 운영 URL을 호출하거나 운영으로 proxy하지 않는다. 기존 빌드는 연결 설정이 맞으면 재사용한다.
- 기존 QA 합성 계정·서명 인증 fixture를 우선 재사용한다. QA 인증은 명시적인 staging 프로필, 검증된 staging 루트, loopback에서만 동작해야 한다. 운영 인증을 수정하거나 공용 로그인 우회 endpoint를 추가하지 않는다.
- 세션 키·쿠키 이름·토큰 서명 재료와 저장 위치를 분리한다. 포트만 다르게 두고 운영 쿠키나 비밀값을 공유하지 않는다. 기존 CSRF·권한 검사는 유지한다. 실제 Google 로그인·OAuth 설정 변경은 이번 완료 조건이 아니다.
- 기존 개발용 인증이 없다면 기존 테스트 fixture의 앱·세션 생성 방법을 격리 실행 도구에서 재사용한다. 비밀번호·쿠키·토큰·키를 보고서나 Handoff에 출력하지 않는다.
- staging의 로컬 백업이 필요하면 staging 폴더만 사용한다. 운영 외장 복사, 운영 보관·삭제 작업, 예약 작업 등록·변경, 서버·터널 자동 기동은 staging에서 실행하지 않는다.
- 운영 GeulbitExternalBackupCopy와 기존 유지보수 작업은 그대로 둔다. staging에서 외장 백업 config나 운영 task identity를 상속하지 않는다.
- start/status/stop은 기존 로컬 실행 방식을 재사용한다. staging PID·실행 경로·포트·시작 정보를 확인한 뒤 자신이 띄운 프로세스만 중지한다. 모든 Python/Waitress 프로세스를 일괄 종료하지 않는다.

원문 없는 합성 자료와 테스트 전용 두 계정으로 진행한다. 초기 구성에서 운영 사용자 글·자료·공용 도서·세션을 가져오지 않는다. R2와 외부 AI는 비활성으로 유지한다.

## 5. 필수 검증

먼저 설정·경로·초기화·세션·작업 격리 targeted test를 실행한다. 그다음 다음 실제 로컬 확인을 수행한다.

1. staging 신규 초기화: 지정 경로, schema 0004, 기존 migration 기록과 DB 무결성·외래키 확인. 반복 초기화 명령이 기존 시험 자료를 지우지 않는지 확인.
2. 계정 A의 새 시험 글 생성 → S4 분석 → 결과 저장 → 재조회 → 글 수정·재분석. 실제 staging 분석 ID와 엔진 식별 정보 기록. 화살표 존재 자체를 성공 조건으로 강제하지 않음.
3. 합성 원작품/파일 하나의 업로드·읽기·삭제가 staging 경로에서만 수행되는지 확인. 계정 B의 A 글·파일·분석 읽기와 변경은 기존 권한 계약대로 거부.
4. 세션 namespace 분리: 임시 두 앱과 별도 합성 비밀값으로 다른 환경의 토큰이 인증되지 않는지 검사. 운영 쿠키·토큰을 가져오지 않음.
5. staging 중지·재기동 후 시험 글·분석 유지. 운영 서비스의 소유 PID·health와 예약 작업 정의는 보존. staging stop이 운영을 건드리지 않음.
6. 잘못된 루트·프로필 누락·운영 alias·포트 충돌·재실행을 검사. staging의 쓰기·삭제·백업·작업 상태 경로가 모두 허용된 테스트 영역에 한정되는지 확인.

검증 실패 시 기존 패치 원칙에 따라 작은 실패 테스트부터 수정·재검증한다. 같은 승인 범위의 반복 보완은 기존 절차로 처리하고 새 복구 Phase를 만들지 않는다. 기대값과 초기화·보존 계약의 충돌을 먼저 검토해 데이터를 지우거나 안전 기대값을 낮춰 통과시키지 않는다.

운영 서비스와 백업 예약 작업은 계속 실행될 수 있다. 운영 DB·WAL·로그의 전체 파일 해시나 예약 작업의 마지막 실행 시각이 자연스럽게 바뀌었다는 이유로 격리 실패를 선언하지 않는다. 이 패치의 실제 쓰기 대상, 프로세스 소유권, 설정·작업 정의, 승인 코드의 보존으로 판단한다. 운영 자료나 비밀값을 감사 로그에 덤프하지 않는다.

보호 코드 28개·고정 자료 39개와 적용된 백업 runtime/config의 기존 기준은 보존한다. 새 개발 파일은 승인 delta로만 기록한다.

전체 223개·57건 재생·합성 24편·전체 build/E2E·p95는 반복하지 않는다. 같은 엔진·의존성의 기존 증거는 재사용하고 이번에는 환경 분리와 새 staging 분석에 집중한다. 공유 초기화/설정을 수정했다면 해당 운영 기본동작 회귀는 임시 환경에서 추가 검사한다.

## 6. 완료·사용·되돌리기

완료 목표:
- IMPLEMENTATION: PASS
- STAGING_READY: true — 초기화와 실제 로컬 사용 확인 완료
- ISOLATION_CHECK: PASS — 지정한 경로·세션·프로세스 분리 검사 통과
- OPERATING_CHANGED: false

테스트 기동·중지·재기동을 확인한 뒤 이번에 띄운 테스트 서버만 정상 종료한다. 수동 시작이 가능한 설정·DB·합성 자료와 정확한 start/status/stop 명령을 남긴다. 무인 상시 실행·예약 자동시작은 추가하지 않는다.

문제가 발생하면 staging 프로세스만 중지하고 후보·로그를 보존한다. 테스트 루트를 자동 통째로 삭제하거나 운영 DB를 과거 백업으로 복원하지 않는다. 운영 백업 패치도 되돌리지 않는다.

사용 안내는 실제 코드 위치, 데이터 루트, 로컬 URL, 시작/상태/종료 명령, 테스트 자료 위치, 보존·정리 주의사항만 짧게 작성한다. reset 기능이 기존에 없다면 새 파괴적 초기화 명령을 이번에 추가하지 않는다.

이번 격리는 같은 Windows 계정 안의 경로·설정·프로세스 분리다. OS 수준의 완전한 보안 sandbox라고 보고하지 않는다. 별도 VM·Windows 계정 구축을 새 필수 조건으로 추가하지 않는다.

S4 운영 새 분석 확인은 USER_ACTION_REQUIRED, 일반 정확도는 BLOCKED_DATA, R2는 DISABLED로 별도 유지한다. 테스트 서버에서 새 분석을 만들었다고 운영 서비스 확인을 PASS로 바꾸지 않는다.

운영 코드/DB/서비스/터널/예약 작업 변경, E: 파일 쓰기, 운영 migration, 실제 Google·사용자 데이터 복제, 버전·공용 자료·UI·튜토리얼 변경, commit/push/merge/deploy를 금지한다. 목표를 달성하면 다음 패치를 자동 시작하지 않는다.
