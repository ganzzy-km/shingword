# 글빛 V2.2 S4 — 브라우저 소비자 계약 보완과 배포 후보 검증 마감

## 목적

엔진 개발을 멈추고 검증된 S4 후보의 남은 기술 검사와 최초 정식 제출을 완료한다. 기존 phaseId `v22-s4-role-coverage-release-prep`를 유지한다. 이번 작업은 운영 배포 승인이 아니다.

AGENTS.md, 최신 S4 실행 계약, api-display-v5 Handoff의 binding.json, browser-fixture-review.json, performance-partial.json, post-http-review.json, reproduction.md만 필요한 범위에서 참조한다. 전체 저장소·과거 Trace를 다시 읽거나 S2/S3/Runner를 재개발하지 않는다.

현재: 기능 223개, 기존57조건·승인16쌍, 합성24편·96회, typecheck/build의 재사용 근거가 있다. 개정 API 4개, 기술63개, 실제 HTTP4조건·DOM24조건·통합6조건은 통과했다. 정식 제출0회이며 R2는 DISABLED다. 후보 보완4회와 이전 계약 개정·실패 기록은 보존한다.

## 2. STALE 검사를 특정 문구가 아닌 실제 endpoint에 연결한다

확인된 결함: 소비자의 '사랑과 희생', '꽃을 지킨다' 치환 대상이 새 승인 fixture에는 없어서 두 편집이 no-op이다. 제품 STALE 결함은 아직 확인되지 않았다.

기존 승인 fixture의 본문·역할·관계·버전·기대값은 변경하지 않는다.

- 실제 argumentLinks의 승인 관계를 선택하고 그 claimId/evidenceId로 정확한 후보를 찾는다. 첫 CLAIM/EVIDENCE를 임의로 가져오지 않는다.
- sourceVersion.content와 writing.content가 같은 초기 상태인지, endpoint span·quote·ID가 일치하는지 먼저 검사한다.
- Python 코드포인트 [start,end) 계약을 따른다. JavaScript UTF-16 slice에 코드포인트 offset을 그대로 넣지 않는다. 기존 변환 helper를 사용할 수 있으면 재사용하고 아니면 이 소비자 안의 작은 순수 helper로 Array.from 기반 처리를 한다.
- claim과 evidence를 각각 독립적으로 편집한다. 선택 endpoint 내부의 실제 문자 1개를 다른 문자로 바꾸되 emoji·문단·코드포인트 길이는 유지한다. 원문 표면 문구나 작품명에 의존하지 않는다.
- 브라우저 조작 전에 editedBody !== originalBody, 변경이 선택 span 내부에만 있음, 다른 endpoint와 나머지 본문은 불변임을 assertion으로 확인한다. no-op, 잘못된 span, quote 불일치는 즉시 실패시킨다.
- claim 편집과 evidence 편집 후 각각 textbox의 실제 값, 기존 STALE 안내, 역할·확정 화살표 숨김을 확인한다. 필드 직접 조작으로 STALE를 강제하거나 API 결과를 지워 통과시키지 않는다.
- 각 검사 사이 원래 본문을 복원하고 기존 역할·승인 화살표가 돌아왔는지 확인한 후 다음 검사를 시작한다. 실제 관찰 조건에 대한 유한 대기를 사용하며 timeout만 늘려 실패를 숨기지 않는다.
- 기존 작품명·탐구 문맥 변경, 화살표 방향·대상 이동, 키보드/터치, 빈 결과, 이전 페이지 이동, 전체 본문 재구성·overflow 검사는 그대로 유지한다.

단위 대조는 같은 helper를 사용하여 수행한다. emoji가 앞에 있는 claim, 1,700코드포인트 이후 evidence, 반복 문구 중 지정된 span만 변경, no-op·잘못된 span 거부를 포함한다. 테스트용 별도 구현으로 통과시키지 않는다.

입력·출력이 같은 artifacts 경로라 과거 증거가 덮어써질 위험이 있으면 이 소비자 파일 안에서만 입력/출력 경로 옵션을 최소 추가할 수 있다. 기본 경로와 JSON 계약은 유지한다. 새 fixture·새 브라우저 프레임워크를 만들지 않는다.

성공 조건: 두 테마 × 1440/820/390px의 6조합에서 claim/evidence STALE 12검사, 복원, 기존 전체 페이지 재구성 검사가 모두 통과한다. ARGUMENT_SMOKE_ONLY=1로 전체 재구성을 건너뛰어 최종 PASS로 처리하지 않는다.

이 스크립트는 실제 Kiwi 결과를 API route fixture로 제공하는 브라우저 소비 검사다. 새로 실제 HTTP 분석을 수행한 검사라고 보고하지 않는다. 기존 실제 HTTP4·DOM24·통합6의 근거와 구분한다.

## 3. 통과한 근거는 재사용하고 미완료 안전 검사만 채운다

독립 Read-only Review가 소비자 수정과 입력 계약을 먼저 검토한 뒤 값비싼 성능 검사를 시작한다.

- 제품·입력·설정·빌드·실행 환경의 연결이 유지되면 기존223개, 57조건·16쌍, 합성96회, typecheck/build, 기술63개, 실제 HTTP/DOM 근거를 재사용한다. 새 실행으로 집계하지 않는다.
- 과거 전체 설치 의존성 해시가 없었다는 v5 제한은 그대로 기록한다. 현재 해시를 과거 해시인 것처럼 채우지 않는다. 환경 불일치가 확인되면 영향받는 검사만 다시 실행한다.
- 이번에 수정한 브라우저 소비 검사는 실제로 새로 실행한다. 다른 HTTP/DOM PASS를 대신 제출하지 않는다.
- 기존 격리 권한 fixture와 실제 출력 경로로 미완료 MATCH_ONLY 검사를 실행한다. JSON, 질문·미리보기, 진단 Trace, 기존 계약상 export/PDF 경로를 빠짐없이 명시한다. 경로를 호출하지 않았거나 출처 처리에 도달하지 않은 것을 누출0 PASS로 삼지 않는다.
- 실제 작품이나 개인정보 대신 기존 허용 합성 원문과 출처에만 있는 식별 문자열을 사용한다. 학생 본문에 이미 있는 같은 문자열과 출처에서 새로 유출된 문자열을 구별한다. 탐지기의 양성 대조와 실제 출력 경로 도달 증거를 남긴다. 원문 전문·비밀값을 로그나 Handoff에 담지 않는다.
- 운영 서버·DB·실계정에는 접근하지 않는다. 기존 임시 QA 호스트·권한 경로를 재사용한다. 실기기 모바일과 실제 Google 로그인은 기존처럼 미검증으로 명시하며 에뮬레이션을 실기기로 보고하지 않는다.

필수 검사 미완료는 다른 검사 PASS로 상쇄하지 않는다. 검증 도구 문제와 제품 오류를 분리하여 기록한다.

## 4. 성능 비교를 끝내고 원시 결과를 즉시 저장한다

기존 run-performance-pair.py와 연결된 격리 측정 절차를 재사용한다. 이번 승인은 실행 산출물의 표본 저장·정상 중단/재개 보완을 포함하지만 측정 대상·타이머 경계·백분위 계산·Gate를 바꾸는 권한은 아니다. 새 성능 플랫폼을 만들지 않는다.

고정 프로토콜: 동일 30,000자 본문과 source fixture, 작품0/1/3개, S3와 S4, 각 warm-up3회·측정30회. cold 비용은 별도 기록한다. 문서가 다른 조건을 요구하면 원본 계약을 확인하여 충돌을 명시하고 조용히 축소하지 않는다.

- 과거 S3 작품0/1개 각30회 요약은 보존한다. 원시행이 없으므로 과거 원시값을 복원했다고 주장하지 않는다. 기존 계약이 요약 receipt 재사용을 허용하고 입력·측정 코드·환경 바인딩이 검증되면 그 그룹만 재사용할 수 있다. 그렇지 않으면 해당 기준 그룹만 재측정한다.
- S3 작품3개는 완료 통계가 없고 S4는 아직 표본이 없다. 필요한 완결 그룹을 실제 측정한다. DB의 completed 건수로 누락된 시간 표본을 만들어내지 않는다.
- 앞으로는 각 표본 종료 즉시 실행ID, stage, sourceCount, input/source hash, sampleIndex, 성공/timeout, elapsed, 관련 환경 hash를 JSONL 등 실행 산출물에 영속 기록한다. warm-up도 표시하되 측정 표본에 섞지 않는다.
- 중단 시 이미 완료된 검증 가능 표본은 같은 실행 계약에서 재사용하고 미완료 표본만 재개한다. 실패·timeout·느린 표본을 임의 삭제하지 않는다. 환경이 달라진 표본을 합산하지 않는다.
- CPU·메모리를 공유하는 브라우저 검사와 성능 측정을 동시에 돌리지 않는다. UI 검사 종료 후 성능을 측정한다. 기존의 불필요한 DB 누적이나 중복 polling이 있다면 먼저 그 측정 계약을 기록하며 제품 경로를 바꿔 속도를 개선하지 않는다.
- 각 sourceCount별 p50/p95와 표본 수를 보고한다. 각각 S4 p95 <= S3 p95×1.5여야 기존 성능 Gate PASS다. 작품0개 결과로 작품1/3개 실패를 상쇄하지 않는다.
- 절대 응답 시간, timeout, 메모리 peak와 종료 후 상태도 기록한다. 이미 보고된 S3 작품1개 p95 20.853초는 부분 기준 관측이며 S4 성능이 아니다. 상대 회귀 Gate만 통과했다고 사용자 체감 속도가 좋다고 단정하지 않는다.

성능이나 필수 안전 검사에서 실제 실패가 나오면 해당 Gate를 유지하고 엔진·임계값·배포 기능을 자동 변경하지 않는다. 원시 결과를 보존한 뒤 가능한 다른 비파괴적 검증은 마무리하여 미완료 목록을 한 번에 보고한다. 보호·정보 노출 문제가 발견되면 즉시 중단한다.

## 5. 최초 정식 제출과 배포 후보 정리

필수 소비자·MATCH_ONLY·성능·Scope·독립 검토가 모두 통과한 정확한 후보만 기존 S4 최초 정식 제출 절차로 보낸다. 후보와 Queue amendment, 빌드, 테스트 결과의 hash를 연결한다. 정식 제출 전까지 원본 worktree를 덮어쓰지 않는다.

기존 Queue가 요구한 정식138개 검증은 최종 후보에서 1회 실행한다. 수를 맞추기 위한 테스트 삭제·skip·xfail은 금지한다. 모든 Gate 통과 시에만 누적5개 파일을 승인된 개발 worktree에 채택하고 PASS_IMPLEMENTATION을 기록한다. 이는 운영 배포가 아니다. 최초 실패 이력·S3 증거·이전 후보는 보존한다.

기존 배포 방식을 바탕으로 실행 전용 산출물에 최종 RC manifest, 검증된 빌드/patch 참조, 실행·중단·rollback 절차, 필수 설정의 이름만 정리한다. 실제 키·DB·개인정보를 복사하지 않는다. 패키지에 QA용 인증 우회·임시 DB·테스트 비밀값이 포함되지 않았는지 확인한다. 새 배포 플랫폼·migration·로그인 체계는 만들지 않는다.

완료 상태는 구분한다.
- IMPLEMENTATION: 정식 통과 시 PASS_IMPLEMENTATION
- TECHNICAL_PREP: 모든 필수 기술 Gate 통과 시 READY_FOR_DEPLOYMENT_REVIEW
- ACCURACY_CERTIFICATION: BLOCKED_DATA
- DEPLOYMENT_AUTHORIZED: false

Phase4A BLOCKED_DATA, Phase4B NOT_STARTED, R2 DISABLED와 G5 기존 판정은 유지한다. 기술 READY는 독립 정답·홀드아웃 완료를 뜻하지 않는다. 제한형 베타로 출시 정책을 바꾸거나 Gate를 면제하는 것도 이번 권한에 포함되지 않는다. 실제 운영 공개는 별도 승인 대상이다.

## 실행 통제와 보고

승인된 위 범위에서는 단계마다 사용자에게 재승인을 요청하지 않고 순서대로 진행한다. 새 제품 오류·범위 초과는 최소 재현과 함께 기록하고 권한을 확대하지 않는다. 소비자 수정 이외에는 엔진·API·UI·R2·Golden·Baseline·기존 테스트 기대값·Runner를 변경하지 않는다. commit/push/merge/deploy 금지.

소비자와 연결된 값싼 계약 검사를 먼저 마친다. 이미 통과한 분석·빌드를 매번 반복하지 않는다. 무관한 리팩터링과 장기 soak test를 추가하지 않는다. 사용한 QA 서버·브라우저는 본 작업 소유임을 확인하고 종료한다.

최종 응답은 STATUS / CHANGED / RULES / TESTED / RISKS만 사용한다.
TESTED에는 신규 실행과 재사용, 브라우저6조합·STALE12검사·전체 재구성, MATCH_ONLY 실제 도달 경로, 성능0/1/3의 기준·S4 p95/비율/표본 수, 정식138개와 제출횟수를 적는다.
