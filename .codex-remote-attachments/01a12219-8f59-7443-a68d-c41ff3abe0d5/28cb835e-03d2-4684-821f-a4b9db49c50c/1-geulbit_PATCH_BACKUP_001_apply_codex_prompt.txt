# PATCH-BACKUP-001 — 외장 사본 격리 복원·운영 적용·자동 복사 활성화

## 목적과 승인 범위
기존 PATCH-BACKUP-001을 마무리한다. 구현을 반복하거나 새 Phase/Runner를 만들지 않는다.

이 프롬프트를 운영 적용 지시로 전달하는 것은 아래 범위의 실행 승인이다.
- 검증된 후보의 런타임 파일·해당 설정만 운영에 적용
- 최초 외장 사본 격리 복원에 필요한 기존 방식의 계획된 서비스 중지·재시작
- 지정 볼륨의 E:\GeulbitBackups와 60분 사본 동기화 예약 실행 활성화
운영 DB 복원·초기화·이전·migration, 디스크 포맷, 다른 서비스 중지, 다른 프로젝트 변경은 승인하지 않는다.

## 기준 확인
AGENTS.md, ACCEPTANCE.md의 패치 규칙, 기존 후보 manifest·검증 receipt·외장 복사 기록의 필요한 항목만 읽는다.

현재 보고된 기준:
- 격리 후보 5개 파일, 신규 31개·관련 회귀 30개 PASS
- E:\GeulbitBackups의 현재 고정 볼륨 ID에 암호화 완료본 1개 복사·재읽기 해시 확인
- 실제 격리 복원 미완료, 운영 코드·예약 작업 미적용
- 로컬 백업 생성 24시간, 로컬 보관 7일, 정상 종료 추가 백업 없음
- 운영 DB C:\Users\USER\GeulbitData\db\geulbit.sqlite3, schema 0004 유지, S4 유지, R2 DISABLED

실제 파일 경로·볼륨 ID·백업 해시·예약 명령은 manifest에서 가져온다. 추측하지 않는다.
최근 승인 변경과 후보의 기준 상태를 대조한다. HEAD만 보거나 현재 파일을 무조건 새 기준으로 채택하지 않는다.
PATCH-ENGINE-001의 실제 새 분석 확인 완료 기록이 있으면 재사용한다. 여전히 미확인이면 사전 확인 자료는 정리하되 서버 중지·운영 적용 전에 USER_ACTION_REQUIRED로 필요한 기존 계정 확인만 남긴다. 엔진 검증을 새로 설계하지 않는다.

## 1. 중지 전 준비
- 후보 5개 중 런타임 적용 파일만 구분한다. 테스트·시험 데이터·비밀값은 운영 배포물에 포함하지 않는다.
- 해당 런타임 파일·설정·영향받는 예약 작업의 변경 전 상태와 복귀 사본을 저장한다. 다른 파일로 범위를 늘리지 않는다.
- 기존 31+30개 검증은 관련 코드·입력·의존성·환경이 일치하면 재사용한다.
- 현재 서비스의 실행 경로·소유 프로세스·원래 실행 상태·처리 중 작업을 확인한다.
- 외장 파일의 바이트 해시와 완료 기록, 고정 볼륨 ID를 확인한다. E: 문자만으로 장치를 신뢰하지 않는다.
- 복원 목적지는 기존 도구가 허용하는 새 격리 디렉터리다. 운영/테스트 데이터 루트와 겹치지 않게 확인한다.
- 현재 백업·복원 도구의 실제 CLI와 보호 조건을 확인한다. 인증·잠금·권한 검사를 우회하지 않는다.

## 2. 실제 외장 사본의 격리 복원
한 번의 계획된 유지보수 구간에서 처리한다.

1. 기존 lifecycle 절차로 새 요청을 막고 진행 중 쓰기·분석 작업이 안전하게 정리됐는지 확인한 뒤 소유한 서비스·터널만 중지한다. 임의 강제 종료하지 않는다.
2. 이미 검증·복사된 외장 .gbb를 복원 입력으로 사용한다. 로컬 파일로 몰래 대체하지 않는다. 도구가 로컬 입력을 요구하면 외장 사본을 격리 위치로 복사하고 입력 해시 연결을 기록한다.
3. 기존 복원 도구의 명시적 권한·검증 절차로 격리 복원한다. 암호화 해제, DB 무결성·외래키·schema, 포함 파일과 기존 격리·세션 무효화 규칙을 확인한다.
4. 운영 DB·업로드·현재 세션·비밀값에는 복원하지 않는다. 복원 결과를 운영 경로로 승격하지 않는다. 평문 복원 자료·개인정보·키를 로그나 Handoff에 넣지 않는다.
5. 복원 실패 시 자동 복사는 활성화하지 않는다. 보존한 운영 코드와 현재 DB로 안전하게 돌아갈 수 있으면 이번 작업이 중지한 서비스만 원래 상태로 복구한다. 안전하지 않으면 원인과 상태를 기록한다.

새 로컬 백업 생성이 필요하면 기존 안전한 백업 절차만 사용한다. 기존 사본으로 충분한 검사를 위해 같은 백업을 반복 생성하지 않는다.

## 3. 검증된 후보 적용과 서비스 정상화
외장 격리 복원 성공 후 기존 배포 방식으로 manifest의 런타임 파일과 최소 설정을 적용한다. 별도 DB/예약 엔진을 추가하거나 기존 코드를 보완하지 않는다.

서비스를 원래 실행 상태로 되돌리고 실제 실행 경로·S4 해시·HTTPS·접근 보호를 확인한다. 기존 DB와 자료가 유지됐는지 읽기 전용으로 확인한다.
처음부터 중지돼 있었거나 사용자가 별도로 STOP한 서비스는 자동 기동하지 않는다. 실패 시 이번 패치 파일·설정만 복귀하며 운영 DB를 과거 백업으로 덮어쓰지 않는다.

## 4. 60분 외장 복사 활성화와 실동작 확인
- 기존 구현된 Windows 예약 실행을 동일 사용자·승인된 권한으로 등록/활성화한다. 사용자 비밀번호를 새 파일에 저장하거나 권한을 확대하지 않는다.
- 작업의 실행 파일·cwd·인수·볼륨 바인딩·60분 간격·중복 실행 방지·PC/로그인 조건을 확인한다.
- 예약 작업에 등록된 실제 명령을 한 번 실행하여 작업 이력과 결과를 확인한다. 로컬에 미복사 완료본이 있으면 복사·재읽기 해시 검증을 확인하고, 이미 동기화됐다면 올바른 SKIPPED_EXISTING 결과를 남긴다. 사본을 삭제해 복사를 억지로 유도하지 않는다.
- 다음 실행 시각과 활성 상태를 기록한다. 수동 실행 1회로 향후 매시간 자동 성공이 보장됐다고 보고하지 않는다.
- 미연결·쓰기 실패 시 비치명적 대기/오류로 끝나고 로컬 백업·운영 서비스는 유지되는 기존 31개 테스트 근거를 재사용한다. 검증을 위해 실제 외장 장치를 강제로 분리하거나 고장을 유발하지 않는다.
- 정기 사본 복사가 서비스·터널을 중지/기동하지 않는지 확인한다. 최초 복원 검사에 필요했던 서버 중지를 매시간 복사에 넣지 않는다.

60분은 완성된 로컬 백업의 누락 사본 확인 주기다. 새 DB 백업 생성은 기존 24시간 정책이고 로컬 보관은 7일이다. 이번 패치에서 정상 종료 추가 백업이나 외장 자동 삭제를 도입하지 않는다.

## 완료·중단
성공 목표:
IMPLEMENTATION: PASS
EXTERNAL_BACKUP: VERIFIED_ON_SELECTED_ARCHIVE
AUTOMATION_APPLIED: true

실제 복원과 실제 예약 명령 검증이 있어야 위 상태를 사용한다. 파일 해시 일치만으로 복원 PASS를 표시하지 않는다.

E:의 Warning은 해결된 것으로 바꾸지 않는다. 이번 승인은 로컬 원본을 보존하는 추가 사본 보관이며 장치 수명·장기 신뢰성 또는 다른 PC의 DPAPI 복구를 보장하지 않는다. 장치 식별 실패·읽기 오류·해시 불일치·복원 실패는 중단 사유다. 폴더 밖 사진·경제 게임 자료를 검사·변경하지 않는다.

예상하지 못한 제품 결함이 나오면 후보와 증거를 보존하고 해당 기능만 미적용/복귀한다. 테스트 기대값·보호 조건을 낮추거나 새 복구 체인을 개발하지 않는다. 전체 엔진·57건·24편·build/E2E를 반복하지 않는다.

독립 정확도 BLOCKED_DATA는 이 저장 보조 패치의 차단 사유가 아니다. R2 활성화, UI·버전·공용 자료·테스트 DB 작업, commit/push/merge는 금지한다.

STATUS / CHANGED / RULES / TESTED / RISKS로만 보고한다.
실제 복원한 외장 사본 ID·해시, 예약 작업명·주기·다음 실행·최근 실행 결과, 재사용한 테스트, 서비스 원상태 복구와 S4/자료 보존, 복귀 기록 위치를 간단히 남긴다. 평문 데이터나 비밀은 첨부하지 않는다.
이번 패치가 끝나면 다음 패치를 자동 시작하지 않는다.
