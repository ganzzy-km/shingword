# PATCH-BACKUP-001 — 기존 암호화 백업의 외장 HDD 자동 복사

## 목표·기준

기존 기능으로 생성·완료 확인된 암호화 백업을 지정한 1.8TB 외장 HDD에 자동 복사하고 검증한다. 운영 DB 이동이나 새 백업 엔진 개발은 하지 않는다.

AGENTS.md, docs/automation/ACCEPTANCE.md의 패치 운영 원칙, PATCH-ENGINE-001의 최신 application-status와 기존 백업 계약을 필요한 부분만 참조한다.

유지할 기준:
- 운영 DB: C:\Users\USER\GeulbitData\db\geulbit.sqlite3
- 스키마: 0004_user_annotations, migration 없음
- 기존 로컬 백업: C:\Users\USER\GeulbitData\operational\local-backups
- 백업 형식: 기존 .gbb와 암호화·격리 복원 방식 유지
- 운영 엔진: 현재 적용한 S4, R2 DISABLED
- 기존 사진·경제 게임·개인 자료는 변경하지 않음

경로는 현재 설정과 대조한다. 불일치하면 자동 교체하지 않는다. 과거 S4 파일을 다시 운영에 덮어쓰지 않는다.
S4 새 분석 확인이 아직 대기여도 격리 구현·테스트는 진행한다. 기존 엔진 적용 상태를 근거 없이 PASS로 변경하지 않는다.

## 1. 최소 탐색·변경 범위

backup_service, 기존 백업 완료 판정, 유지보수·예약 실행 진입점, 관련 테스트를 symbol → 정의 → 호출부 순으로 확인한다. backend/app/services/backup_service.py부터 확인하되 실제 구현 위치를 우선한다.

허용 범위는 백업 사본 동기화 로직, 기존 실행 기반에 연결하는 최소 호출부·설정, 관련 targeted test다. 실제 변경 파일 목록을 한 번 확정해 기존 패치 계약에 기록한 뒤 진행한다. 필요 없는 파일을 채우거나 경로를 추측해 복제하지 않는다.

기존 함수로 처리 가능하면 재사용한다. 별도 암호화 엔진, DB, 범용 작업 큐, 상주 데몬, 새 Runner를 만들지 않는다. 실행 기록·설정은 기존 승인된 위치를 사용하며 DB 스키마는 변경하지 않는다.

이번에는 버전 표시, 공용 자료 전환, UI·튜토리얼, 테스트 서버 DB 생성, 경제 게임 백업, 로컬 백업 생성 시점·보관 기간 변경을 함께 구현하지 않는다.

## 2. 외장 장치 지정

기존 설정이나 사용자 지정 기록에 외장 대상이 있으면 재사용한다. E:라는 문자나 1.8TB라는 용량만으로 대상을 자동 선택하지 않는다.

장치 지정에는 확인 가능한 볼륨 식별 정보와 대상 폴더를 함께 묶는다. 확정된 HDD 아래 GeulbitBackups 전용 폴더와 이 기능이 만든 파일에만 쓰기를 허용한다. 경로 이탈·다른 볼륨·심볼릭 링크/재분석 지점에 의한 우회를 막는다. 드라이브 문자가 재사용돼도 다른 장치에 복사하지 않는다.

대상이 아직 지정되지 않았다면 기본 비활성 설정과 모의 파일시스템으로 구현·테스트를 마친다. 실제 장치 지정만 CONFIGURATION_REQUIRED로 보고한다. 비공개 경로를 추측하거나 이 때문에 새 Runner 개발을 시작하지 않는다.

대상 확인 후 전용 폴더에서만 작은 쓰기·읽기 검사를 수행한다. 포맷, 파티션 변경, 전체 디스크 검사·복구, 사진 폴더 탐색은 하지 않는다.
exFAT라는 이유만으로 완성된 백업 사본 복사를 자동 금지하지 않는다. 운영 DB의 기존 파일시스템 검사 정책은 그대로 둔다. 과거 Warning은 확인 필요 사항으로 남기며 작은 검사 통과를 HDD 전체 정상 판정으로 표시하지 않는다.

## 3. 복사·검증 규칙

1. .gbb 확장자만 보지 말고 기존 도구의 완료 기록·검증 정보로 확정된 백업만 선택한다. 생성 중인 파일, 임시 파일, 운영 SQLite·WAL·SHM, 평문 DB는 대상에서 제외한다.
2. 원본 백업은 읽기 전용으로 사용한다. 기존 백업 정리 작업과 충돌하지 않게 기존 잠금/수명 관리가 있으면 재사용한다. 복사 도중 원본이 바뀌거나 사라지면 실패 처리하고 완료로 기록하지 않는다.
3. 메모리에 파일 전체를 올리지 않고 스트리밍 복사·해시 계산을 사용한다. 목적지의 고유 .partial 파일에 복사하고 쓰기 완료 처리 후 목적지 파일을 다시 읽어 크기와 SHA-256을 대조한다.
4. 원본 안정성·대상 장치 일치·해시가 모두 확인된 경우에만 충돌 없이 최종 이름으로 확정하고 완료 기록을 남긴다. 복사 시작 및 완료 확정 전에 대상 볼륨을 확인한다. 해시 검증을 정전 내성·장치 수명 보장이라고 설명하지 않는다.
5. 같은 이름·같은 내용의 사본은 검증 후 건너뛴다. 같은 이름·다른 내용이면 기존 사본을 덮어쓰지 않고 충돌을 기록한다.
6. 동시 실행은 사본 동기화 작업끼리만 직렬화한다. 운영 DB 잠금을 잡아 분석·저장을 지연시키지 않는다. 재실행·중단 후에도 중복 사본과 잘못된 완료 기록이 생기지 않도록 한다.
7. 분리·쓰기 권한 부족·용량 부족·해시 불일치는 그 사본의 실패로 기록한다. 로컬 원본은 보존하고 다음 기회에 재시도한다. 정리 가능한 것은 이 동기화 작업이 만든 식별 가능한 임시 파일뿐이다.
8. 이 기능은 추가 복사다. 로컬에서 삭제된 오래된 백업을 외장에서도 삭제하는 미러링, 외장 자동 보관 정리, 원본 이동은 하지 않는다.
9. 로그에는 백업 식별자·해시·상태·필요한 오류 정보만 기록한다. 본문, 토큰, DPAPI 비밀값, 복호화 데이터는 출력하지 않는다. 실제 사용자 백업은 Handoff에 넣지 않는다.

## 4. 자동 실행 연결

기존 백업 성공 이후와 기존 유지보수·예약 실행 주기에 미복사 완료본 확인을 연결한다. 사용자가 호출할 수 있는 일회성 동기화 명령도 기존 CLI에 최소 추가하거나 재사용한다.

대용량 복사를 요청 처리나 서비스 시작·종료의 대기 경로에 넣지 않는다. 기존 실행 기반을 우선 사용한다. 별도 실행이 불가피하면 기존 Windows 예약 작업 방식의 작은 사본 동기화 작업 하나까지만 사용하고 사용자 지정 장치 확인 전에는 활성화하지 않는다.

HDD를 다시 연결하면 다음 점검 주기에 현재 남아 있는 미복사 완료본을 재시도한다. 즉시 감지용 새 장치 감시 시스템은 만들지 않는다. 실제 점검 간격과 서버가 꺼졌을 때 실행 여부를 결과에 명시한다.

HDD가 없어도 서비스·로컬 백업은 정상 유지한다. 무한 재시도, 오류 팝업 반복, 서버·터널 자동 기동을 금지한다. 기존 수동 STOP을 취소하지 않는다.

24시간 로컬 백업 생성, 정상 종료 추가 백업 등은 기존 기능의 현재 지원 상태만 확인한다. 미지원이라고 이번에 스케줄·서비스 중지 정책까지 바꾸지 않는다. 누락 기능은 후속 한 항목으로 기록한다.
외장 미연결 중 기존 로컬 보관 정책으로 삭제된 사본은 복사할 수 없음을 기록한다. 이 패치에서 로컬 보관 정책을 몰래 변경하지 않는다.

## 5. 관련 테스트와 실제 확인

먼저 임시 폴더·모의 장치로 다음 targeted test를 실행한다.
- 완료 암호화 파일만 선택하고 생성 중·평문 DB·WAL·SHM 제외
- 정상 복사와 목적지 재읽기 해시 일치
- 동일 사본 재실행에서 중복 없음, 같은 이름 다른 내용 덮어쓰기 없음
- 미연결, 분리, 용량·권한 오류, 해시 불일치, 원본 변경·삭제
- 다른 볼륨 또는 전용 폴더 밖으로 쓰기 차단
- 중복 실행·중단 후 재시도, 실패한 사본을 완료로 표시하지 않음
- 로컬 원본·기존 사진·타 프로젝트 자료 보존
- 오류가 서비스 시작·종료·분석·기존 백업을 방해하지 않음

통과 후 기존 백업·암호화·유지보수 중 변경에 직접 영향받는 테스트만 실행한다. 엔진 223개, 에세이 24편, 57건 재생, 전체 build/E2E를 반복하지 않는다.

대상 HDD가 확인돼 있으면 검증된 완료 백업 한 개를 실제 복사하고 해시를 확인한다. 그 외장 사본을 기존 복원 도구로 격리 복원해 무결성을 검사한다. 복원 도구의 권한·격리 조건을 우회하지 않으며 운영 DB에는 복원하지 않는다. 장치 미지정이나 복원 권한 부족은 해당 실제 검사만 미완료로 표시한다.

## 6. 채택·종료

정상·오류·재시도 관련 테스트 통과, 관련 회귀 없음, S4·Golden·Baseline·기존 보호 자료 보존이면 IMPLEMENTATION: PASS로 기록한다. 패치 계약에 등록한 설정·호출부 변경은 별도 승인 delta로 연결하고 기존 snapshot·실패 이력을 재작성하지 않는다.

실제 장치 확인과 복사·격리 복원까지 통과하면 EXTERNAL_BACKUP: VERIFIED로 구분한다. 구현 PASS와 외장 실제 검증을 합치지 않는다.

현재 요청은 구현과 격리 검증까지 수행한다. 운영 코드 적용·예약 작업 활성화는 기존 S4 새 분석 확인 및 외장 대상 확인 뒤 사용자 승인된 적용 단계에서 진행한다. 진행 중인 서버를 임의로 중지하거나 운영 설정을 자동 변경하지 않는다.

문제가 있으면 이번 범위에서 원인을 확인하고 최소 수정 후 실패 테스트부터 재검증한다. 합격을 위해 기존 암호화·권한·보호 기대값을 낮추지 않는다. 범위 밖 재설계가 필요하면 해당 후보만 보존하고 종료한다. 새 복구 Phase를 자동 생성하지 않는다.

운영 DB 이전·초기화·migration, 외장 포맷, 다른 자료 삭제, 경제 게임 수정, R2 활성화, commit/push/merge/deploy는 금지한다. 독립 정확도 데이터 부족은 이 저장 보조 패치의 구현을 차단하는 사유가 아니다.

종료 보고는 STATUS / CHANGED / RULES / TESTED / RISKS만 사용한다.
STATUS에서 IMPLEMENTATION, EXTERNAL_BACKUP, AUTOMATION_APPLIED를 구분한다.
TESTED에는 명령·exit code·통과 수와 실제 외장 복사/격리 복원 여부만 적는다.
RISKS에는 필요한 장치 지정, 실제 점검 간격, 미검증 사항, 남은 자동 백업 생성 연결만 간단히 적는다.
완료하면 다음 패치를 시작하지 않는다.
