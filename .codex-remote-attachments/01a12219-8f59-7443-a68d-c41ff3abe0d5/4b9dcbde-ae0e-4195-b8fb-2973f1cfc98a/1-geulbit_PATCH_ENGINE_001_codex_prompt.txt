# PATCH-ENGINE-001 — S4 최종 검증·필요한 수정·실제 서비스 적용

## 목표와 권한

검증된 S4를 마지막으로 확인하고 적용에 필요한 결함만 수정한 뒤, 현재 글빛 서비스가 실제로 S4로 새 에세이를 분석하도록 전환한다. 후보 검증이나 개발 worktree 채택만으로 완료하지 않는다.
이 프롬프트를 실행하라는 사용자 지시는 아래 범위의 백업, 기존 검증된 배포 절차, 대상 서비스 전환·재시작, 비식별 시험 자료 확인을 승인한다. 불특정 다수 공개, 가입 정책 확대, 새 OAuth 설정, 다른 기능 출시를 승인하지 않는다.

현재 목적은 소수 지인이 쓰는 학생 개인 프로젝트다. 독립 에세이 48편·인적 라벨 부족을 이번 적용의 차단 조건으로 요구하지 않는다. ACCURACY_CERTIFICATION=BLOCKED_DATA는 사실대로 유지한다. R2는 DISABLED다.
버전 1.0.0 표시, 공용 자료 전환, UI 정리, 튜토리얼은 별도 패치다. 이번에는 수정하지 않는다. 면책·시험버전 안내 팝업도 추가하지 않는다.

AGENTS.md, docs/automation/ACCEPTANCE.md, 최신 S4 v6 PASS receipt와 배포 manifest, 동봉한 geulbit_S4_engine_reference.txt의 0~3절부터 확인한다. 문제 발생 시 관련 절만 추가로 읽는다.
과거 no-deploy·정확도 미인증 차단을 이번 제한된 적용 요청과 혼동하지 않는다. 기존 기록은 보존하고 이번 승인·정책 차이를 새 패치 기록에 명시한다.

## 1. 시작 상태와 범위를 한 번에 확인한다

- S4 최종 소스·빌드·의존성·실행 설정과 PASS receipt의 연결을 확인한다. S4 엔진 참고 SHA는 0ffebe4ad0121f488185d2fcba82fdcf17bc16f3a82ca03a03d6f712b9f84696 이다. 다른 값이면 후속 승인 변경인지 확인하고 옛 파일로 덮어쓰지 않는다.
- 현재 개발 작업본과 실제 서비스의 실행 루트, 프로세스·서비스 관리 명령, Python 환경, 프론트 배포물, DB 버전과 데이터 경로를 구분한다. 오래된 Windows 경로나 HEAD 하나만으로 일치를 판단하지 않는다.
- 현재 운영이 이미 동일 S4라면 재복사하지 않고 실제 새 분석으로 확인한다. 적용 대상이 불명확하거나 다른 프로젝트이면 임의로 선택하지 않는다.
- 패치의 baseline→candidate→실제 배포 파일 목록을 만든다. 각 파일의 전후 hash와 필요한 이유를 남긴다. 검증된 전체 runtime 의존 경계를 확인하며 structure.py 하나만 복사하지 않는다.

이번 승인 범위는 S4의 기존 분석 경로와 그 직접적인 호환·배포 연결이다.
중심 파일: backend/app/analysis/structure.py, snapshot.py, source_context.py, backend/app/v2/analysis_api.py.
직접 필요한 기존 morphology·quotation·ruleset 모듈, argument-spans 및 ArgumentText/ArgumentEditorLayer 연결, 실제 사용 중인 배포·실행 설정은 검증된 S4 의존성을 적용하거나 S4 호환 결함을 고치는 경우에만 포함한다.
관련 engine/v2 테스트와 scripts/verify-argument-links.cjs도 같은 결함의 검증 범위에 포함한다. 기존 테스트를 복제하거나 임의로 새 경로를 만들지 않는다.

실제 경로·수정 필요 파일·test node를 선별해 기존 패치 등록 방식으로 한 번 고정한다. 단순 파일 수 상한 때문에 필요한 소비자 검사를 누락하지 않는다. 다른 UI, 인증 정책, 원문 공개 권한, 새 DB 설계, Runner 엔진 수정으로 범위를 넓히지 않는다.
산출물은 기존 output 루트의 새 PATCH-ENGINE-001 디렉터리에만 추가한다. 과거 snapshot·receipt·실패 이력을 덮어쓰지 않는다. 별도 대형 보고서나 복구 체인은 만들지 않는다.
이번에 명시한 적용·수정 경로가 기존 보호 목록과 겹치면 해당 파일의 변경 전 해시와 원본 증거를 보존하고 그 경로만 새 승인 delta에 연결한다. 다른 보호 항목은 유지한다. 실제 변경된 승인 파일까지 모두 해시 불변이라고 보고하거나 보호 목록 전체를 새 기준으로 덮어쓰지 않는다.

## 2. 마지막 기능 검증은 기존 근거를 재사용한다

코드·입력·설정·환경이 같은 기존 223개, 57조건·승인16쌍, 합성96회, build·브라우저·성능 근거를 다시 실행한 것처럼 세지 말고 재사용한다. 다르면 영향받는 항목만 실행한다. 수를 맞추려 테스트를 지우거나 skip하지 않는다.

현재 후보의 API 연결에서 다음 동작을 관련 기존 fixture로 확인한다.
- P06/D01 해석 CLAIM과 기존 근거·ID·span 보존.
- N03/N08/D03의 역할 6개 복구. 원문 미선택과 제목 fixture 모드를 구분.
- 읽기 절차, 현실 학교 규정, 앞절 개념어의 잘못된 역할 승격 없음.
- 동일 명사구의 품사·분절 차이 허용, 다른 이름·소유격·문맥의 잘못된 병합 없음.
- R0의 4/6점 REVIEW는 대상 관계가 존재하되 화살표 없음. 기존 8점 승인 양성은 표시됨.
- R1 직접 지시의 정상 승인과 복수 사건·원거리 보류 유지. R1에 R0의 7점 기준을 강제하지 않음.
- 연결 모드의 N08 대상 쌍은 실제 출처 정책을 거쳐 REJECTED. 미선택 모드의 NOT_REACHED를 같은 성공으로 세지 않음.
- 같은 작품 다른 판본, 실제 비교, '비교적', 제목 '에서는' 처리 유지.
- REVIEW/REJECTED의 확정적 질문 없음. 기존 정상 질문과 구버전 snapshot 정상.

화살표 수를 늘리는 것을 완료 조건으로 삼지 않는다. 24편 전체 반복과 긴 성능 재측정은 실제 엔진 수정으로 기존 근거가 무효가 된 경우에만 수행한다.

## 3. 문제가 있으면 같은 패치에서 수정하고 계속 검증한다

실패를 제품 결함 / 배포·호환성 / 테스트·fixture 계약 / 환경 / 알려진 정확도 한계로 분류한다. S4 참고 문서의 관련 원칙과 최소 입력으로 최초 실패 지점을 확인한다.
승인된 기능 경계 안의 결함은 최소 수정→실패 테스트→직접 영향 suite 순으로 해결한다. 보완은 최대 3사이클이며 같은 원인에 진전 없이 2회 반복하면 증거와 함께 중단한다. 사이클은 본질적인 후보 수정 단위이며 pytest를 여러 번 실행한 횟수가 아니다. 과거 이력은 초기화하지 않는다.

주장 역할 추가 시 기존 근거 보존처럼 실제 계약과 충돌한 단계 한정 테스트는 근거를 적고 명시적으로 개정할 수 있다. 기존 입력·기대값을 별도 보존하고 양성·음성·보존 검사를 함께 유지한다. 점수/임계값 완화, Golden 정답 변경, 실패 삭제·skip, 후보 결과를 정답으로 복사하는 행위는 금지한다.
범위 안의 타당한 테스트 개정이나 최소 호환 수정마다 새 프롬프트를 요구하지 않는다. 보안 계약 변경이나 전면 재설계가 필요하면 적용하지 않고 정확한 추가 범위만 보고한다.

엔진이 바뀌면 보정된 후보의 새 SHA·이유를 기록한다. 원본 S4 해시나 옛 PASS를 새 코드의 증거로 재사용하지 않는다. 결과 형식·의미가 달라질 때만 기존 방식의 버전·검증기·소비자 호환성을 함께 검토한다. /8을 /9로 일괄 치환하거나 과거 저장 결과를 재작성하지 않는다.

## 4. 최소 통합 확인 후 실제로 전환한다

배포 전:
- 기존 로그인·권한을 유지한 격리 환경에서 글 입력→저장→분석→조회→수정→재분석을 한 흐름으로 검사한다. 현재 사용하는 브라우저 크기에서 승인 표시와 실제 endpoint 편집 STALE·복원을 확인한다.
- 변경 영향이 있는 권한·MATCH_ONLY 실제 출력 경로를 확인한다. 해당 경로를 호출하지 않은 채 누출0으로 통과시키지 않는다. 기존 검증이 그대로 유효하면 재사용한다.
- frontend·빌드 설정이 안 바뀌었으면 검증된 build를 재사용한다. 바뀌었으면 최종 후보에서 한 번만 typecheck/build한다.
- 현재 사용 환경에서 짧은 글과 기존 30,000자 fixture를 완료까지 실행해 오류·timeout·메모리를 확인한다. 원작품 연결은 사용할 모드에서 확인한다. 몇 회의 smoke 결과를 p95나 장기 안정성 인증으로 표시하지 않는다. 느리지만 완료되는 기존 동작만으로 새 최적화 프로젝트를 시작하지 않는다.

적용 전 현재 실행물·필수 설정·사용자 DB의 복귀 수단을 확보한다. 기존 백업 도구를 사용하고 SQLite/WAL의 실행 중 파일을 무작정 복사하지 않는다. 비밀값·실제 글은 보고서나 Handoff에 포함하지 않는다.
DB 스키마 변경 없는 전환을 우선한다. 현재 DB와 S4에 이미 검증된 마이그레이션이 꼭 필요하면 정확한 버전을 기록하고 격리 복사본에서 적용·복원 확인 후 그 기존 스크립트만 실행할 수 있다. 새 migration 생성, 추측한 0004→0005 실행, 데이터 초기화는 승인하지 않는다. 안전한 기존 경로가 없으면 운영 변경 전에 중단한다.

통과하면 중간 재승인을 반복 요청하지 말고 기존 배포 절차로 진행한다.
1. 새 요청/쓰기를 잠시 제한하고 진행 중 작업을 확인한다. 다른 프로세스를 일괄 종료하지 않는다.
2. 확정된 manifest의 runtime 파일·필요한 build/설정만 전환한다. 개발 저장소 전체나 tests·QA 인증 우회·임시 DB를 운영으로 복사하지 않는다. 운영의 무관한 변경을 덮어쓰지 않는다.
3. 식별된 글빛 서비스만 재시작한다. 기존 도메인·접근 범위·인증 설정은 유지한다.
4. 다음 적용 후 검사를 통과한 뒤 정상 사용을 재개한다.

## 5. '실제 적용'을 증명한다

- 운영 서비스 프로세스의 실행 명령·루트·환경과 승인 runtime 파일 해시를 대조한다. 기존 로컬 진단/시작 로그를 사용한다. 필요하다면 비밀값 없는 일회성 로컬 시작 식별 기록만 사용하고 외부 인증 우회·디버그 endpoint를 열지 않는다.
- 승인된 시험 계정에서 비식별 글로 실제 서비스 API의 새 분석을 생성한다. 새 analysis run ID·입력 version ID, 대표 S4 역할 복구, 승인/REVIEW/출처 거부와 화면의 연결을 확인한다.
- 기존 정상 글의 읽기·저장·재분석과 과거 결과 조회가 유지되는지 최소 확인한다. 다른 사용자 데이터의 본문은 수집하지 않는다. 테스트에서 만든 자료만 기존 정상 경로로 정리한다.
- R2 비활성, 사용자 간 접근 차단, MATCH_ONLY 보호, 편집 시 STALE와 재분석 후 최신 결과를 확인한다.

파일 복사, health 200, 제품 표시 버전, /8 또는 /9 문자열만으로 ENGINE_APPLIED=true라고 보고하지 않는다. 다른 디렉터리의 단독 python 명령 결과도 실제 서비스가 로드한 증거로 삼지 않는다. 재시작된 대상 서비스와 실제 신규 분석이 함께 확인돼야 한다.

적용 후 주요 흐름·데이터·권한 검사가 실패하면 추가 공개 전에 기존 절차로 복귀한다. 서비스 쓰기 제한 상태와 데이터 변경 여부를 확인하고 새 사용자 글을 지우는 DB 복원은 하지 않는다. 코드/스키마 호환 복귀가 불가능하면 양쪽 자료를 보존하고 서비스를 안전하게 중단한다.

## 완료 기준과 보고

목표는 IMPLEMENTATION=PASS, ENGINE_APPLIED=true, POST_DEPLOY_SMOKE=PASS다. 본문 저장·조회 정상, 대표 S4 새 분석 확인, 기존 결과 보존, 권한·원문 보호, R2 비활성이 모두 필요하다.
미적용이면 '검증 완료'와 '운영 적용 완료'를 구분하고 차단 원인을 남긴다. 정확도 미인증 자체는 지인 시험 적용을 중단시키지 않는다.

사용자의 이번 승인은 이 엔진 전환에 한정된다. Google 설정·공용 자료·버전 표기·UI·튜토리얼·상시 안내문을 바꾸지 않는다. commit/push/merge, 기존 이력 삭제, 자동 공개 대상 확대, 새 Runner·병렬 엔진 개발은 금지한다.

최종 보고는 STATUS / CHANGED / RULES / TESTED / RISKS만 사용한다.
STATUS에 IMPLEMENTATION, ENGINE_APPLIED, POST_DEPLOY_SMOKE, ACCURACY_CERTIFICATION, R2를 적는다.
CHANGED에 실제 대상 서비스·파일·최종 SHA·S4 보정 여부와 복귀 자료 위치를 적되 비밀값을 출력하지 않는다.
TESTED에 새 실행/재사용, 고친 오류, 실제 서비스의 새 분석 증거를 구분한다.
RISKS에는 남은 알려진 한계와 미검증 범위만 적는다. 간단한 적용 receipt를 남기고 목표 달성 즉시 종료한다.
