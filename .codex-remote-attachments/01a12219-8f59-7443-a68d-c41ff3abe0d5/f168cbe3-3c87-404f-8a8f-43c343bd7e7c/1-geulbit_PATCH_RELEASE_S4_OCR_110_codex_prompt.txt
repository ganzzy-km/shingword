## 1. 단일 후보 구성과 충돌 방지
1. 현재 실제 운영 HEAD·서비스 PID·실행 코드 경로·DB/업로드 루트·배포/백업 바인딩을 읽기 전용으로 기록한다. 이전 S4 적용 후 인증 계정의 신규 분석은 미확인으로 기록돼 있으므로 확인 없이 PASS로 바꾸지 않는다.
2. OCR Handoff의 `source/`·증분 patch·빌드와 최신 운영본을 비교한다. OCR 후보는 이전 PATCH-VERSION-001·PATCH-LIB-001·UI-INPUT 변경을 기반으로 만들었을 수 있으므로 App.tsx, library_api.py, analysis_api.py 등의 겹치는 변경을 구체적으로 확인한다. 이미 승인한 기능을 중복 개발하지 않고 S4·백업 기능을 잃지 않게 필요한 delta만 통합한다. 미승인 기능·비밀 설정을 암묵적으로 추가하지 않는다.
3. 내부 S4 분석 ID·스냅샷·OCR 모델 fingerprint와 DB revision은 유지한다. 제품 사용자 표시 버전만 기존 package.json 단일 원본에 맞춰 1.1.0으로 정리한다. 별도 시험판/면책 팝업은 만들지 않는다.
4. 실제로 수정이 필요한 API, Worker, UI 소비자, 설정 바인딩과 관련 테스트의 파일을 한 번에 확인해 이번 패치의 허용 범위로 기록한다. 기존 Runner/공통 배포 엔진을 새로 만들거나 기회주의적 리팩터링을 하지 않는다.
5. 운영 OCR 실행 환경은 기존 운영 웹 Python과 격리된 Windows CPU OCR venv, 고정 가중치, Tesseract exe/tessdata_best, PDFium 라이브러리, PP-StructureV3, 선택적 VL의 **실재 파일과 SHA/버전/라이선스 고지**를 확인한다. Handoff ZIP은 모델·EXE·DLL 자체를 포함하지 않는다. 자동 온라인 다운로드를 서비스 시작·업로드 경로에 넣지 않는다. OCR_LOCAL_CONFIG는 검증된 로컬 설정으로 서비스 프로세스에만 바인딩하고 기존 Google/ngrok/DPAPI 비밀·인증 설정은 변경하지 않는다. 설정의 resourceEvidence 경로·해시가 실제 실행 환경에서 유효한지 확인한다.

## 2. S4 + OCR의 기능·정확도·자원 최종 점검 및 필요한 수정
기존 검증 자료는 코드·모델·환경·입력이 같으면 재사용한다. 수정한 부분만 작은 실패 사례부터 targeted test한다. 한 번의 최종 후보에서 관련 통합 검사를 수행한다.

S4: 현재 검증된 구조/관계/출처 정책과 기존 승인 16쌍·57조건을 보존한다. 이전 운영 파일 적용 기록과 현재 실제 프로세스의 엔진 SHA를 대조한다. 새로운 S4 분석 생성, DB 버전별 저장·재조회, 질문·REVIEW·STALE, 원작품 출처가 다른 근거의 비승인, MATCH_ONLY 출력 보호를 확인한다. 운영 인증 새 분석의 실제 증거가 없다면 독립적인 확인 대기로 기록한다. 새 S4 알고리즘을 재설계하지 않는다.

OCR: 정상 텍스트 PDF의 직접 추출, 스캔 시·산문·희곡, 혼합 PDF의 중복 방지, 일반과 고정밀의 서로 다른 실행 경로, 좌표·행·연/문단·화자 후보 표시, 국소 PSM6/7·Paddle, 수동 영역 VL, 검수·확정 판본·UTF-8 TXT/구조 JSON·S4 재사용을 확인한다. 다크/라이트, 1440/820/390px, 모달 X/ESC·초점 복원, 미저장 보호를 필요한 화면만 확인한다. OCR Worker 재시작·취소·중단 재개와 정상 에세이 분석 공존을 시험한다. 사용자 자료를 외부 AI로 전송하지 않는다.

품질 판단: 현재 합성 12페이지의 엄격 CER는 일반/고정밀 각각 128/963=13.29%로 같았고 실제 문학 정답은 0페이지였다. 이를 정확도 개선 PASS로 재분류하지 않는다. 이미 구현된 구조 메타데이터·검수·재인식 경로를 유지하고, 실제 재현되는 잘림/글줄 누락/잘못된 순서/공백 손실과 안전한 개선 규칙만 보완한다. 시·소설·희곡 위주의 권리 확인된 원문과 독립 대조 텍스트가 현재 준비돼 있으면 같은 페이지 쌍체 평가(CER, 구조, 줄 누락, 새 오수정, 검수량)를 실행한다. 없다면 QUALITY_ADVANTAGE=UNVERIFIED_DATA로 명시하며 합성 결과나 S4 에세이를 인적 정답으로 위조하지 않는다. 검수 완료 결과와 자동 초안을 혼합해 성능을 주장하지 않는다. 근거 없는 문자/공백/문장부호 자동 생성, 확정 판본 덮어쓰기, 숫자 목표를 맞추기 위한 데이터/테스트 변경은 금지한다.

성능: 기존 일반 OCR 최초 102.64초·재실행 8.41초 현상의 원인을 로그 계측(큐 대기, 모델 최초 로드, 파일 렌더, 실제 추론, 저장)으로 제한적으로 확인하고 재현되는 결함만 수정한다. 5분 이내 중심의 현실적인 안정성 검사에서 S4·OCR 동작, 호스트 가용 RAM/commit, Worker Job 전체 커밋 피크를 측정한다. VL 실측 7.85GiB와 S4 메모리 예약을 고려해 기존 JobObject·입장 제한을 유지한다. 자동 VL 동시 실행/전체 페이지 VL/무제한 대기열은 추가하지 않는다. 초회 지연의 원인을 파악하지 못하면 UNKNOWN으로 남기고 무작정 별도 서비스 시스템을 새로 만들지 않는다.

보안: 업로드 형식·크기·페이지·작업 수·시간 제한, IDOR/CSRF, 원본/크롭·OCR 대안·TXT/JSON/다운로드 권한, MATCH_ONLY, 공개 중지 후 기존 분석 조회, 개인 데이터 수명, 작업 재시도·중복 확정 방지를 관련 API 테스트로 확인한다. STAGING 전용 로그인 우회·`/__staging__` 경로가 운영 런타임에 포함되거나 접근 가능하면 출시를 중단한다.

## 3. STAGING 최종 통합 검증
운영 원본을 복제하지 않은 테스트 DB(C:\Users\USER\GeulbitStagingData)를 사용한다. 실제 운영본 + 검증된 OCR delta를 병합한 **단일 최종 후보**로 필요 범위의 테스트, typecheck/build 및 다음 기능 연속 흐름을 확인한다.
- PDF 업로드 → 일반·고정밀 선택 → OCR 진행 → 원문 대조·구조 검수 → 확정 새 리비전 → 자료실/공용 범위 조회 → S4 새 분석 생성·저장·재조회
- 독립 두 시험 계정의 접근 권한, MATCH_ONLY 원문 비노출, 공개 중지, STALE/ESC 및 취소, 중단·재개
- 실제 CPU 런타임 바인딩, 빠른 모드가 무거운 모델을 부르지 않음, 고정밀 선택 영역 VL은 자원 입장 판정 준수
기존 138/111/223 등의 이전 PASS를 단순 합산하지 않는다. 사용한 exact command/exitCode/pass/환경·해시와 재사용 근거만 기록한다. 검증 후 이번 STAGING 서버만 종료하고 이전 binding·빌드를 복구한다.

## 4. 실제 운영 적용 전 필수 Gate
A. 최신 서비스 DB·소스·OCR 모듈 충돌과 개인정보·권한 경계가 설명 가능한 단일 승인 delta일 것.
B. 제품 코드/빌드/모델/환경·경로의 해시와 OCR 전용 venv 실행이 검증될 것. 기존 인증/운영 URL·비밀·자동 외장 백업이 보존될 것.
C. 0004 DB 유지, 예상치 못한 schema migration 0, 오프라인 Worker와 실제 업로드·S4 연결이 STAGING에서 검증될 것.
D. 운영 서버의 기존 lifecycle·쓰기 정지 방식으로 일시 중지 가능한지 확인. 새 글을 잃지 않도록 변경 직전 최신 암호화 백업 생성, 실제 도구의 격리 복원·무결성 확인, 코드/빌드/config 복귀 사본과 manifest SHA를 준비할 것. E: Warning과 과거 예약 exit1은 숨기지 말고 C 로컬 백업 보호 유지.
E. IDOR·MATCH_ONLY·자료 공개 범위·검수 확정본 보존과 주요 사용자 흐름의 차단 결함이 0건일 것.
기능·안전 Gate 충족 시 지인 시험 사용을 위한 운영 배포를 진행한다. 실자료 정답이 없다면 정확도 우위/1% 목표는 UNVERIFIED로 남기되, 이를 소규모 시험 사용의 자동 차단 조건으로 바꾸지 않는다. 다만 명백한 원문 누락·자료 노출·데이터 손상·반복 OOM이 남아 있으면 BLOCKED로 중단한다.

## 5. 운영 적용과 적용 후 확인
위 Gate가 모두 통과하면 이미 소유권과 PID가 확인된 운영 lifecycle만 이용해 새 작업 접수를 잠시 중지하고 Writer·OCR 작업을 안전하게 정리한다. 이전 서버/터널과 예약 작업의 통제 방식을 재사용한다. 현재 DB·파일·세션·DPAPI 비밀값과 E: 자동 복사 설정은 보존한다. 검증된 delta 및 정적 빌드만 교체하고 index.html은 기존 안전 배포 순서에 따라 마지막에 적용한다. OCR 전용 고정 런타임/config만 추가 바인딩하고 필요한 운영 프로세스를 한 번 재시작한다. 운영 DB를 과거 파일로 덮어쓰지 않는다.

배포 직후 소유 프로세스·SHA·앱 버전 1.1.0 표시, 로컬/외부 HTTPS, 비인증 보호 응답, Google 세션·기존 글·분석 조회, OCR 업로드→일반/고정밀→검수→확정→S4의 새 분석 저장·재조회, 모델 실제 선택 기록, 워커 완료/재개, 기존 백업 예약 상태를 확인한다. 운영 검증은 테스트/허용된 자료와 계정으로만 수행한다. 실제 로그인 사용자 동작이 필요한 경우 정직하게 USER_ACTION_REQUIRED로 남긴다. 가짜 운영 인증 경로를 만들거나 ID를 조작하여 PASS 처리하지 않는다. 인증 확인이 불가능하더라도 비인증 검사/소스 확인의 성공은 별도로 기록하고, 추가 동작이 필요한 사용자에게 한 번에 정확한 행동만 요청한다.

배포 오류 시 이번 delta만 복귀한다. 새 OCR 초안·리비전·사용자 데이터가 있으면 이전 버전과 호환되는지 먼저 판단하고 데이터 손실 없는 경로만 사용한다. 운영 DB를 옛 백업으로 덮어쓰거나 시험/운영 서버를 혼동하지 않는다. 복귀 불가능한 데이터 충돌이 확인되면 신규 OCR만 중지하고 자료를 보존한 채 BLOCKED로 보고한다.
