# PATCH-LIB-001 — 기존 업로드 자료의 관리자 공용 전환

## 1. 목표와 승인

관리자가 이미 업로드한 원작품·참고자료를 재업로드 없이 공용으로 전환하고 공개 중지할 수 있게 한다. 기존 자료실의 화면·API·공개 범위·권한 판정을 우선 재사용한다.

이번 요청은 격리 개발본 구현, 필요한 시험 계정·자료 생성, 실제 STAGING UI/API 검증까지 승인한다. 운영 적용이나 실제 사용자 자료의 공개 전환은 수행하지 않는다.

AGENTS.md, docs/automation/ACCEPTANCE.md의 패치 원칙, 최신 PATCH-VERSION-001 완료 receipt·patch, PATCH-STAGING-001의 STAGING.md만 필요한 범위에서 참조한다. 이전 Phase와 Runner를 재개발하지 않는다.

출발점:
- 현재 운영에 적용된 S4와 PATCH-BACKUP-001 변경을 보존한다.
- PATCH-VERSION-001의 검증된 변경분을 포함한 후보를 사용한다. package.json.version 단일 원본과 설정의 ‘글빛 1.0.0’ 표시를 유지한다.
- 버전 패치 검증 후 STAGING의 이전 빌드가 복원됐다. 현재 실행 폴더에 버전 패치가 이미 있다고 가정하지 말고 receipt·변경분을 연결한다. 이전 후보 전체를 덮어쓰지 않는다.
- 테스트: C:\Users\USER\GeulbitStagingData / https://localhost:8786 / schema 0004
- 운영: C:\Users\USER\GeulbitData — 쓰기·재시작·배포 대상 아님.

## 2. 필요한 코드만 확인하고 Scope 확정

자료실의 기존 자료 선택·상세·관리 버튼 → 프론트 API 호출 → 서버 공개 범위 변경·접근 검사 → 자료/작품/판본 연결 → 관련 테스트 순으로 탐색한다.

참고 위치는 src/WorkLibrary.tsx, src/Library.tsx, src/api.ts와 backend/app/v2의 library_api.py, work_library.py, files.py다. 실제 symbol 위치를 확인하고 필요한 범위만 읽는다. 이 목록 전체를 수정하거나 없는 위치에 복제 파일을 만들지 않는다.

이미 공용 전환 API가 있다면 UI 연결·권한·갱신 문제를 먼저 고친다. 새 endpoint는 기존 기능으로 처리할 수 없을 때에만 기존 라우트 구조 안에 최소 추가한다. 메서드·요청·응답·오류 계약을 실제 코드로 확인한다.

허용 기능 범위는 자료 공개 범위 변경, 해당 UI/API/직렬화·선택 권한 연결, 직접 관련 테스트와 격리 시험 fixture다. 실제 파일 목록과 산출물 위치를 최초 한 번 확인하여 기존 패치 계약에 등록한다. 이번 명세는 이 범위의 실제 경로 등록을 승인한다. 임의의 작은 파일 수 때문에 우회 코드나 별도 엔진을 만들지 않는다.

0004의 기존 필드와 저장·권한 구조로 구현한다. DB migration, 공용 자료용 중복 테이블·파일 복제, 범용 권한 시스템 신설은 하지 않는다. 스키마 변경 없이는 구현할 수 없다면 근거와 최소 변경안만 남기고 자동 확대하지 않는다.

## 3. 기능 계약

### A. 대상과 권한
- 공용은 기존 앱에서 자료를 사용할 자격이 있는 로그인 사용자의 공용 자료실을 뜻한다. 비로그인 인터넷 공개나 정적 public 폴더 이동이 아니다.
- 관리자 본인 소유 자료 또는 기존 시스템에서 명시적으로 관리·공개 권한이 부여된 자료만 전환한다.
- 다른 사용자의 개인 자료를 관리자라는 이유만으로 찾아보거나 가져오는 기능은 추가하지 않는다.
- 개인 에세이, 분석 결과, 사용자 주석은 대상이 아니다.
- 서버에서 인증·ADMIN 권한·대상 자료의 변경 자격·CSRF를 확인한다. 클라이언트의 ownerId, role, 공개 가능 플래그를 신뢰하지 않는다.
- 필요한 최소 식별자와 목표 공개 상태만 변경한다. 공개 전환 요청으로 소유자·원문 이용 권한·임의 필드를 함께 변경하지 못하게 한다.

### B. 공용 전환
- 기존 자료 상세/관리 영역에 ‘공용으로 전환’을 제공한다. 별도 대형 관리자 화면은 만들지 않는다.
- 전환 전 해당 자료 유형의 기존 필수 메타데이터와 공개 가능 상태를 확인한다. 누락 시 구체적인 항목만 알리고 기존 편집 기능을 이용한다. 새로운 증빙 제출 시스템은 만들지 않는다.
- 선택한 기존 자료와 판본에 필요한 공개 범위만 변경한다. 같은 작품의 다른 개인 문서·판본·연결 에세이를 함께 공개하지 않는다.
- 자료 ID, 판본 ID, 본문·파일 해시, 소유자, 기존 분석 참조는 유지한다. 재업로드·재추출·재분석이나 중복 자료 생성은 하지 않는다.
- 자료와 작품 목록에서 함께 쓰는 상태가 있다면 기존 저장 계층의 트랜잭션으로 일관되게 갱신한다. 실패 시 일부만 공개된 상태를 남기지 않는다.
- 공용 자료가 기존 개인 자료 만료 처리로 잘못 삭제되지 않는지 기존 공개 자료 보호 규칙을 재사용해 확인한다. 보관 기간 자체를 새로 바꾸지 않는다.

### C. 공개 중지
- 공용 상태인 대상에는 ‘공개 중지’를 제공하고 기존 개인 접근 정책으로 되돌린다. 누가 계속 볼 수 있는지는 기존 소유·관리 권한을 따른다.
- 일반 사용자 공용 목록·검색·새 분석용 선택에서 제외한다. 화면에 남은 오래된 ID를 제출해도 서버가 현재 권한을 재검사한다.
- 원문 보기·다운로드 등의 새 요청도 현재 권한으로 검사한다.
- 기존 저장된 글·분석·인용 참조·주석은 삭제하거나 재작성하지 않는다. 과거 분석 조회와 현재 원문 접근 권한을 구분한다. 연결이 사라졌다는 이유로 기존 분석 화면이 오류를 내지 않아야 한다.
- 전환 endpoint에서 자료 삭제·만료 처리를 실행하지 않는다. 공용 중지 후 적용되는 기존 보관 정책은 임의 초기화하거나 변경하지 않는다.

### D. 원문 권한·재시도
- 공개 범위와 원문 이용 권한은 독립이다. MATCH_ONLY는 공용 전환 후에도 전문 보기·다운로드가 허용되지 않는다. 허용된 원문 열람 자료는 기존 열람 권한을 유지한다.
- 원문을 프론트에 추가로 내려 보내거나 메타데이터·검색·오류 응답·새 로그에 포함하지 않는다.
- 이미 공용인 자료를 다시 공용으로 요청하거나 이미 중지된 상태를 재요청해도 중복 생성·불필요한 판본 변경이 없어야 한다.
- 상태 변경은 성공 응답 뒤 목록·상세에 반영한다. 기존 캐시 갱신 방식을 재사용한다.
- 기존 변경 이력이 있으면 관리자, 자료 식별자, 전후 상태, 시각을 기록한다. 없다면 기존 감사 로그 방식으로 최소 기록하며 새 감사 DB를 만들지 않는다. 원문·토큰은 기록하지 않는다.

## 4. UI 범위

기존 자료 목록·상세에서 다음만 추가·연결한다.
- ‘개인’ / ‘공용’ 상태
- 관리자용 ‘공용으로 전환’ / ‘공개 중지’
- 짧은 공개 대상 확인과 처리 중·실패 상태

개인 자료 공개는 의도적인 사용자 동작으로만 실행한다. 확인창에는 자료 식별과 변경 범위만 짧게 표시한다. 성공 뒤에는 상태 갱신이나 간단한 알림이면 충분하다.

일반 사용자에게 관리 버튼을 노출하지 않는다. 반복 클릭을 막고 실패 시 이전 표시 상태를 보존한다.

‘시험 버전’, ‘공개 베타’, 면책·환영 문구를 추가하지 않는다. 문구 일괄 정리, 튜토리얼, 대규모 UI 개편, 일괄 공용 전환·사용자 등록 신청 기능은 이번에 구현하지 않는다.

## 5. STAGING 실제 검증

STAGING.md의 실제 시작·상태·종료 명령을 재사용한다. 이번 후보 코드·빌드가 실제로 제공되는지 경로와 해시로 확인한다. 운영 API로 요청이 가지 않아야 한다.

시험 관리자 1명과 기존 일반 계정 student-a/student-b를 사용한다. 관리자 세션은 기존 격리 QA/fixture 방식으로 만든다. 기존 일반 계정을 관리자로 승격하거나 운영 인증·OAuth를 변경하지 않는다. 시험 인증은 STAGING·loopback 전용으로 유지하며 운영 패치에 포함하지 않는다.

기존 시험 DB·글·분석을 초기화하지 않는다. 이번 패치 전용 합성 자료만 추가하고 작업 목록을 남긴다. 실제 운영 원작품이나 타인 글을 복제하지 않는다.

최소 시험 자료:
- 관리자가 업로드한 비공개 MATCH_ONLY 자료 1개
- 기존 정책상 열람 가능한 관리자 자료 1개
- 일반 사용자 A의 개인 자료 1개

구현 전에 역할별 허용/거부 기대조건을 고정한다. 이번 요구와 충돌하는 ‘기존 자료는 항상 개인이어야 함’ 같은 단계 한정 테스트는 전환 전/후 계약으로 명시적으로 개정할 수 있다. 다른 사용자 자료 보호나 MATCH_ONLY의 제한을 완화하지 않는다. Golden·과거 동결 기록은 변경하지 않는다.

검증 순서:
1. 새 공개 범위·권한·반복 요청·실패 rollback targeted tests.
2. 영향받는 기존 자료실·파일 접근·소유권·CSRF·보관 정책 테스트만 실행. 최종 후보의 typecheck/build를 각각 한 번 통과시키고 해당 빌드를 STAGING에 연결.
3. 실제 관리자 UI로 기존 업로드 자료를 공용 전환하고 일반 계정에서 목록·검색·선택 확인.
4. 일반 계정의 직접 API 전환·비인증·CSRF 누락 요청 거부. 타인 개인 자료는 전환/조회 불가.
5. MATCH_ONLY는 공용 목록에서 선택 가능하되 API·보기·다운로드의 제한 유지. 기존 출력 경로 관련 보호 검사는 변경 영향에 맞춰 실행.
6. 일반 계정에서 공용 자료로 새 시험 분석 1건을 저장한다. 원작품을 선택했다는 이유로 화살표 발생을 강제하지 않는다.
7. 관리자가 공개 중지한 뒤 일반 목록·새 선택·원문 접근이 차단되고 기존 저장 분석은 정상 조회되는지 확인. 같은 요청 재실행에서 중복·손실이 없는지 확인.
8. 실제 자료/판본 ID·본문/파일 해시·기존 시험 글·분석 보존을 확인.
9. 두 테마와 1440/820/390px에서 버튼·상태·처리 오류를 확인하고 ‘글빛 1.0.0’ 표시 보존. 브라우저 문제로 소스를 수정했다면 영향 검사와 최종 빌드만 다시 수행.
10. 시험 서버 재기동 뒤 공개 상태 유지와 운영 서비스·백업 설정 보존 확인.

실제 공개 전환 성공을 DB 직접 UPDATE로 대신하지 않는다. fixture 준비와 기능 검증을 구분한다.
새 테스트 실패 시 가장 작은 실패부터 보완한다. 같은 기능 범위에서 수정·검증을 이어가며 새 Runner 복구 체계를 만들지 않는다.
제품 전체 223개, 에세이 57건, 합성 24편 전체, p95, Google 실계정 검증을 이유 없이 반복하지 않는다. 관련 코드·입력·환경이 같은 기존 증거는 재사용한다.

## 6. 완료·보존·보고

완료 조건:
- 관리자의 기존 자료 전환과 공개 중지가 UI/API에서 정상.
- 일반 사용자는 공용 자료를 선택할 수 있으나 상태를 변경할 수 없음.
- 선택한 자료 외 개인정보·자료의 공개 확장 없음.
- 원문 이용 권한·ID/판본·기존 분석 참조 보존.
- 관련 테스트·STAGING 실제 사용·필요한 build 통과.
- 버전 1.0.0과 S4·외장 백업·운영 데이터·보호 자료 보존.

검증 후 이번에 띄운 STAGING 서버만 종료한다. 제공 빌드와 프로세스 설정을 임시로 바꿨다면 이전 상태로 복원하고 최종 후보·검증 자료를 별도 보관한다. 다른 테스트 자료를 삭제하거나 DB를 과거 백업으로 덮어쓰지 않는다.

Handoff에는 이번 패치, 실제 변경 파일 목록, 코드·빌드 해시, 적용/복귀 방법, 필요한 시험 fixture 식별자와 결과만 보관한다. 버전 패치에서 이번 패치로 이어지는 누적 변경분을 구분하여 1.0.0 표시를 잃지 않게 한다. 비밀값·실제 사용자 자료·STAGING 인증 도구를 운영 배포 묶음에 넣지 않는다.
