# 글빛 V2.2 — S3 격리 후보 보완: 해석 보어절과 독서 절차 구별

## 목표
P06·D01의 CLAIM_CANDIDATE 복구를 유지하면서 S3 독립 검토에서 발견된 독서 절차 오탐 2건을 해결한다. 관계 승인 수를 늘리는 작업이 아니다.

AGENTS.md, 현재 S3 실행 계약, 최신 Checkpoint와 Handoff의 다음 부분만 참조한다.
- final-read-only-review.json
- review-blocker-reproductions.json의 original/candidate 2건
- S3.patch의 analyze_structure 변경부
- test_interpretive_claim_candidates.py 및 test-expectations-freeze-v2.json
S2 전체 진단, 대형 snapshot, 이전 개발 보고서는 다시 읽지 않는다.

## 실행 범위
기존 S3 phaseId와 검증된 Runner를 유지한다. formalPhaseStarted=false, formalRunnerAttempts=0, submittedToWorktree=false인지 실제 현재 상태와 대조한다.
현재 문제는 Runner 오류가 아니므로 Runner 수정, 복구 체인 신설, 이전 시도 횟수 초기화를 하지 않는다.

수정 허용 파일은 다음 2개뿐이다.
- backend/app/analysis/structure.py
- backend/engine_tests/test_interpretive_claim_candidates.py
maxChangedFiles: 2

현재 개발 worktree와 기존 실패 후보·receipt를 보존하고 별도 격리 후보 리비전에서 보완한다. 이번 명세는 동일 Scope 내 추가 후보 보완 1사이클을 대상으로 한다. 과거 candidateRepairAttempts=1 이력을 지우지 않는다. 사전 테스트 실패와 정식 Runner 제출 횟수는 기존 계약대로 구분하여 기록한다.
새 실행 결과와 추가 기대조건은 기존 S3 출력 루트의 새 하위 디렉터리에 저장한다. 기존 Queue·Checkpoint·동결 파일을 덮어쓰지 않는다. 실제 경로·기준 해시·Scope는 수정 전에 한 번 확인한다.

## 이미 확인된 원인
analyze_structure의 신규 work_interpretation은 complement 전체에서 INTERPRETATION_NOUNS를 any()로 찾는다. interpreted_process도 관형형 및 서술어 존재만 확인하므로 다른 수식절의 개념 명사와 독서 절차를 잘못 결합한다.

실제 실패 입력:
A. 이 작품은 음성 합성 프로그램이 의미 단위를 나누어 처리하는 과정으로 읽힌다.
B. 이 작품은 독서 경험이 부족한 학생들이 발음을 연습하는 과정으로 읽힌다.

두 입력 모두 원본에는 없던 EXPLICIT_INTERPRETIVE_READING과 CLAIM_CANDIDATE가 후보에서 추가됐다.
A의 ‘의미’는 ‘의미 단위’의 일부이고 중심 동작은 처리다. B의 ‘경험’은 학생을 수식하는 구절에 있으며 중심 동작의 대상은 발음이다.
본문 어디엔가 개념 명사가 있다는 조건으로 해석 단서를 만들지 않는다.

## 수정 조건
1. 신규 EXPLICIT_INTERPRETIVE_READING 경로만 수정한다. 기존 다른 claimSignals나 역할을 문장 전체에서 제거하는 필터를 만들지 않는다.
2. 기존 Kiwi 토큰·원문 위치를 재사용해 ‘읽히다’에 직접 연결된 ‘명사+(으)로’ 구간과 그 명사를 수식하는 중심 서술 부분을 제한적으로 확인한다. Kiwi 품사만으로 완전한 의존구문이 제공된다고 가정하지 않는다.
3. 수식절 내부 명사, 별도 주어를 수식하는 명사, 복합 명사의 일부를 직접 해석 근거로 승격하지 않는다. ‘경험을 받아들이는 과정’과 ‘경험이 부족한 학생들이 발음을 연습하는 과정’을 구분한다. ‘의미 단위를 처리하는 과정’도 ‘의미’ 하나로 통과시키지 않는다.
4. 중심 동작·직접 대상이 문자 처리, 낭독, 발음 연습 등 실제 독서 절차를 가리키는 경우 신규 해석 cue를 주지 않는다. 관계가 충분히 확인되지 않으면 이 신규 경로에서는 승격하지 않는다. 기존의 다른 주장 판정은 그대로 유지한다.
5. ‘음성’, ‘독서’, ‘발음’, ‘의미’, ‘경험’이 문장 어디든 있으면 차단하는 금칙어 방식은 금지한다. 작품 속 독서 행위를 해석하는 문장까지 일괄 차단하지 않는다. ‘이 작품은’ 주어를 통째로 제외해 반례를 우회하지 않는다.
6. P06·D01뿐 아니라 기존 긍정 사례 ‘이 작품은 낯선 경험을 받아들이는 과정으로 읽힌다.’를 유지한다. essayId, 작품명, 전체 문장 하드코딩을 금지한다.
7. 직접 인용·전언·종결 의문·외부 부정에 대한 신규 cue 보호를 유지한다. 내부 수식절의 부정과 ‘읽히지 않는다’의 부정을 구별한다. 부정문은 모두 주장이 아니라는 전역 규칙을 추가하지 않는다.
8. 문장 ID·코드포인트 span, E1 역할, R1 모호성 검사, 점수·임계값·margin·출처 정책·질문 정책은 유지한다. R2, N03/N08/D03의 별도 역할 누락, 다른 기능은 수정하지 않는다.

형태소·구조 경계와 판정 사유가 확인되는 최소 규칙 하나로 구현한다. 단순 단어 목록 추가로 두 문장만 막거나 새 파서·의미 모델을 도입하지 않는다. 미지원 구문을 지원된 것처럼 주장하지 않는다.

## 구현 전 고정할 검증
기존 31개 테스트의 기대값은 유지한다. 다음 2개 실패 문장을 회귀 테스트로 추가하고 source/claimSignals 변화까지 확인한다.
- 실패 A, B: 신규 cue 없음. 이 두 최소 입력에서는 CLAIM_CANDIDATE도 없음.
- P06·D01 C2: CLAIM_CANDIDATE 유지, E1·ID·span 보존.
- 기존 긍정 ‘이 작품은 낯선 경험을 받아들이는 과정으로 읽힌다.’ 유지.

다음 대조 검사는 새 DEVELOPMENT_EXPECTATION으로 실행 전에 고정한다. 독립 인적 정답으로 표시하지 않는다.
- 독서 절차 문장에 ‘의미·경험’ 수식어를 넣거나 빼도 이 신규 경로로 승격되지 않음.
- 해석 문장의 배경 수식어에 ‘발음 연습’이 있어도 그 단어만으로 차단되지 않음. 예: ‘이 작품은 발음 연습에 매달리던 인물이 타인의 경험을 받아들이는 과정으로 읽힌다.’
- ‘이 행동은 속도를 줄이지 않는 과정으로 읽힌다.’의 내부 부정 긍정 사례 유지.
- 기존 인용·전언·부정·복수 사건·원거리 지시·교차 작품 보호 유지.

기대조건 간 충돌이 확인되면 증거와 충돌 항목을 기록한다. 결과를 보고 기대값을 낮추거나 과거 동결 파일을 덮어쓰지 않는다. 새 테스트 추가로 바뀐 테스트 파일 해시는 별도 receipt에 기록한다.

## 검증 순서
1. 새 반례·대조 테스트와 P06·D01 최소 테스트부터 실행한다.
2. 통과하면 S3 신규 테스트 전체와 기존 보호 93개를 실행한다. 테스트 개수만 맞추지 말고 기존 node ID·assertion의 보존을 확인한다.
3. P06·D01 두 모드를 재검증한다. 네 REVIEW 관계의 기존 MULTIPLE_EVENTS_IN_PREVIOUS_SENTENCE 사유를 보존한다. 승인·화살표 생성을 합격 조건으로 요구하지 않는다. 질문은 실제 문자열·연결 대상까지 비교한다.
4. 최종 후보에서 기존 검증된 57건 재생을 1회 실행한다. 승인 16쌍 보존, 설명되지 않은 역할·관계·질문 변경 0건을 확인한다.
5. 보호 파일 28개·고정 자료 39개, 원본 worktree, 메인 Checkpoint의 무결성과 Scope를 확인한다.
6. 독립 Read-only Review는 새 후보 해시에 연결한다. 기존 31개 통과만으로 완료 처리하지 말고 이번 반례와 대조 조건을 함께 검토한다.

엔진이나 R2 전체 재탐색, 매 수정마다 24편 전체·전체 unit·build·E2E 반복은 하지 않는다. 새로운 범위 밖 결함은 별도 기록하고 수정하지 않는다.

## 완료와 제출
다음 조건을 모두 만족하면 READY_FOR_S3_SUBMISSION이다.
- P06·D01 주장 복구 유지.
- 알려진 독서 절차 반례와 사전 고정 대조 조건 전부 통과.
- 기존 31개 기대조건 및 보호 93개 통과.
- 기존 57건·승인 16쌍 보존, 설명되지 않은 질문·관계 회귀 0건.
- Scope·무결성·독립 Review PASS.

검증된 단일 후보만 기존 승인 S3 절차의 최초 정식 제출 대상으로 사용한다. 현재 실행 계약과 분석 버전·불변성 계약이 제출을 허용하는지 확인한다. 미충족 계약이 있으면 후보를 보존하고 필요한 최소 변경만 보고한다. Runner나 다른 제품 파일을 자동 수정하지 않는다.
정식 S3 검증까지 통과했을 때만 PASS_IMPLEMENTATION으로 기록한다. 독립 검토나 필수 조건 실패 시 BLOCKED_REGRESSION을 유지하고 추가 자동 보완 없이 종료한다.

Phase 4A BLOCKED_DATA, R2 DISABLED, Phase 4B NOT_STARTED는 유지한다. 운영 DB·서버·UI 접근 및 commit/push/merge/deploy는 금지한다. 일반 정확도 PASS를 주장하지 않는다.
