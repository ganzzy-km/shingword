# 글빛 2.0 분석 엔진 알고리즘

## 확정 경계

Kiwi와 로컬 규범 ruleset을 사용한다. 주장·근거 후보와 관계 신호를 제공한다. 모든 본문 위치는 입력 버전의 code point 좌표에 연결한다. 기본 UI와 책장 UI가 같은 분석 결과를 표시한다. AI는 질문 전용이며 분석 엔진의 판정이나 교정에 사용하지 않는다.

규범 위반 후보, 문장 역할 후보, 관계 신호와 의미 유사도를 서로 다른 결과로 취급한다. 프로그램의 수치를 교사의 점수로 표시하지 않는다. 분석 불가나 근거 부족을 0점으로 치환하지 않는다. 아래 실행 순서는 기존 모듈과 확정 목표를 연결한 제안이며 세부 가중치가 확정됐다는 뜻은 아니다.

## 입력과 실행 순서

1. 서버에서 접근 권한과 불변 essay_version을 확인한다. 분석 옵션과 필요한 자료 Revision을 고정한다. engine과 ruleset 식별자를 실행에 연결하는 필드 설계는 제안이다.
2. 원문 기준 인용 범위와 문단 및 문장 구간을 계산한다. 따옴표 내부 문장부호를 문장 끝으로 무조건 처리하지 않는다. 반복 구절도 위치로 구별한다.
3. Kiwi로 형태소, 표면형, 기본형, 품사와 복수 후보를 얻는다. 신뢰도와 분석 실패를 보존한다. 미등록어를 곧바로 오타라고 확정하지 않는다.
4. 로컬 ruleset으로 맞춤법과 문법 후보를 생성한다. 규칙 식별자, 출처, 조건과 제안 근거를 연결한다. 직접 인용 내부는 원문 대조가 필요한 가능성으로 표시하고 자동 수정 적용을 막는다.
5. 주장, 근거, 설명, 효과와 탐구 질문 연결 후보를 만든다. 관찰 신호와 판정 근거를 제공한다. 후보 없음과 판단 보류를 허용한다. 기존 단일 역할 결과를 정답 라벨로 승격하지 않는다.
6. 후보 사이의 관계 신호를 계산한다. 같은 문단, 거리, 연결 표현, 공유 주제 표현과 후속 설명은 기존 신호의 재사용 후보이다. 논리적 타당성이나 인과 증명을 확정하지 않는다.
7. 의미 비교가 필요한 경우 주체, 대상, 서술어, 극성, 양태와 인용 구조를 비교한다. 형태소 신뢰도와 의미 유사도를 분리한다.
8. 자료가 선택된 경우 해당 DocumentRevision의 인용 구간과 대조한다. 단어·공백 유사성이 원문 일치나 동일 판본의 증명이 되지는 않는다.
9. 기존 PEEL 및 평가 기준 모듈은 독립된 참고 결과로 통합한다. 계산 가능한 분모가 없으면 계산 불가를 표시한다. 2.0의 수치 산식과 표시 기준은 확정 계약을 확인한다.
10. 모든 결과를 같은 analysis_run과 입력 버전에 연결한다. 취소와 실패를 성공으로 바꾸지 않는다. 부분 결과의 공개 범위와 상태 전이는 API 계약에서 확정한다.

## 기존 알고리즘 관찰

`backend/app/analysis/engine.py`의 classify_role은 연결 표현을 순서대로 검사해 단일 역할을 반환한다. 효과 표현 → 근거 표현 → 설명 표현 → 탐구 질문 핵심 표현 중첩 → 길이 20 이상 주장 후보 → 미분류 순이다. 반환 신뢰도 상수는 통계적으로 보정된 확률이라는 근거가 없다.

argument_links는 주장 뒤의 가장 가까운 근거 문장을 선택한다. 같은 문단 2, 두 문장 이내 2, 공유 용어 두 개 이상 2, 공유 용어 존재 1, 연결 표현 1, 후속 설명 2를 합산한다. 합 7 이상은 연결 가능성 높음, 4 이상은 연결 보완 필요, 나머지는 연결이 불분명함이다. shared terms를 sameSubject로 이름 붙인 기존 신호는 실제 주체 일치의 증명이 아니다. 이 수치와 한 쌍 선택 방식은 구형 구현 관찰이며 2.0 확정 알고리즘이 아니다.

`integration.py`는 morphology, semanticRoles와 quotations를 통합하며 compare_semantics를 별도 호출한다. 기존 README와 RESEARCH_NOTES는 의미 판정 0.85와 0.65를 프로젝트의 공학적 휴리스틱으로 설명한다. 논문의 평가 점수나 확정 규범이 아니다. 수치를 재사용하려면 실제 thresholds 정의와 관련 회귀 사례만 추가 확인한다.

따라서 2.0 후보와 관계 신호 계약을 만들 때 기존 결과를 근거와 함께 재사용할 수 있다. 후보 개수, 관계 대상 범위, 신호 가중치, 임계값, 문장 길이 기준과 신뢰도 표시 방식은 미결이다. 단순 길이로 주장을 확정하거나 공유 단어 수로 의미·논증을 확정하지 않는다.

## 의미 비교의 차단 신호

기존 설계 설명은 긍정과 부정, 주체와 대상 교환, 사동과 피동, 수치, 날짜, 고유명사, 양태, 인용 내용과 주체, 비교, 인과 및 핵심 서술 관계의 차이를 차단 신호로 다룬다. 단어가 비슷하더라도 같은 의미를 자동 확정하지 않는다. 정확한 차단 조건과 예외는 기존 semantic_compare 정의와 targeted test를 기준으로 확인한다. 판단 보류는 정상 결과이다.

## code point 앵커 계약

확정된 좌표 단위는 Unicode code point이다. 제안하는 앵커는 version_id, start_cp, end_cp, quote를 가지며 구간은 시작 포함과 끝 제외인 [start_cp, end_cp)로 표현한다. 필드명과 구간 형식은 아직 확정 wire schema가 아니다.

앵커가 유효하려면 입력 버전이 일치하고 `0 <= start_cp <= end_cp <= code_point_length(text)`이며 해당 구간과 quote가 일치해야 한다. 일반 피드백의 빈 구간 허용 여부는 미결이다. 오류가 있으면 이동과 적용을 비활성화한다. 문자열 검색으로 첫 번째 같은 구절에 대체 연결하지 않는다.

예를 들어 문자열 `가😀나`의 code point 경계는 0, 1, 2, 3이고 JavaScript UTF-16 경계는 0, 1, 3, 4이다. emoji의 code point 구간 [1, 2)는 DOM 선택 구간 [1, 3)에 대응한다. code point가 화면의 한 글자나 grapheme cluster와 항상 같다고 가정하지 않는다.

Python의 문자열 좌표와 프론트의 UTF-16 좌표 사이에 검증된 변환 지도를 사용한다. 문단·문장·형태소의 상대 위치는 원문 절대 위치로 변환한다. Kiwi 반환 오프셋의 실제 단위는 라이브러리 계약과 테스트로 확인하고 무조건 code point로 간주하지 않는다. NFC나 줄바꿈 변환이 있다면 변환 전후 지도 또는 동일 문자열 계약이 필요하다.

책의 각 페이지는 같은 입력 버전의 연속 code point 구간을 갖는다. 페이지를 순서대로 결합하면 원문과 정확히 같아야 한다. 화면 크기와 메뉴 상태가 달라지면 페이지 번호 대신 원문 위치로 이동한다. 편집 이후 예전 분석 앵커를 직접 재사용하지 않는다. 검증된 편집 범위 지도만 사용하고 출처를 증명할 수 없으면 재분석을 안내한다.

## 재현성과 성능

같은 입력 버전, 규칙 버전, 분석기 버전과 옵션을 기록해 결과 차이를 설명할 수 있어야 한다. 실행 시간이나 ID는 재현성 비교 대상에서 제외한다는 방식은 제안이다. ruleset 업데이트와 Kiwi 버전 정책, 사용자 역할 수정의 재분석 처리 방식은 미결이다.

이미 검증된 모듈을 다시 구현하지 않는다. 문장 및 후보 인덱스를 재사용하고 외부 호출을 기본 분석 경로에서 제외한다. 캐시와 병렬 처리 수치는 실측 후 결정한다. 10,000과 30,000 code point 입력으로 처리 시간, 메모리, Unicode 보존을 측정한다. 기본 안정성 검사는 짧은 고속 시뮬레이션과 약 5분을 우선한다. 허용 지연과 메모리 상한은 미결이며 과거 페이지 분할 통과를 전체 엔진 성능 통과로 표시하지 않는다.
